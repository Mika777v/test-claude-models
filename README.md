# test-claude-models

Claude のモデルおよび AI 駆動開発の運用方法を比較・検証するためのリポジトリ。

## 背景

Claude には複数のモデルが存在する。

1. Fable
2. Opus
3. Sonnet
4. Haiku

一般的に上から順に高性能だが、その分利用コストも高くなる。
（Fable は追加課金が必要なため、本検証では主に Opus / Sonnet / Haiku を対象とする）

AI 駆動開発を実践する中で、単純なモデル性能だけではなく、

- コンテキスト量
- 応答時間
- 利用コスト
- 保守性
- 要件解釈の精度

が開発効率に大きく影響することが分かった。

特に大規模なプロジェクトでは、AI に大量のコードやドキュメントを読ませ続けることで、トークン消費やコストが大きく増加する。

そのため、

- ドキュメント整備は本当に効果があるのか
- ルールは品質向上に寄与するのか
- 上位モデルと下位モデルをどう使い分けるべきか

を定量的に検証したいと考えた。

## 検証したいこと

### 1. モデル比較

対象:

- Opus
- Sonnet
- Haiku

比較項目:

- 実装速度
- トークン消費量
- 推定コスト
- テスト成功率
- 要件解釈の精度

---

### 2. ルール有無の比較

対象:

- bare
  - ドキュメントなし
- minimal
  - ドキュメントあり（参照指示なし）
- template
  - AGENTS.md / CLAUDE.md による運用

比較項目:

- 実装コスト
- 品質
- ドキュメント更新率
- ADR 作成率
- 勝手な仕様変更率

---

### 3. 曖昧な要求への対応

例:

- 「使わなくなったルートを片付ける」

比較項目:

- 確認質問をしたか
- 勝手に仕様を決めたか
- DB スキーマ変更の有無
- ADR 作成の有無

---

### 4. 保守性の比較

初回実装だけでなく、

- 権限追加
- 検索条件追加
- API変更
- DB変更

などの継続開発を行い、

- 修正コスト
- 影響範囲
- AI の判断品質

を比較する。

## 仮説

### 仮説1

0→1 開発では

```
bare > minimal > template
```

の順でコストが低い。

### 仮説2

1→10 開発や保守では

```
minimal > template > bare
```

の順で安定する。

### 仮説3

ルールの価値は「コード品質向上」ではなく、

- 勝手な仕様変更を防ぐ
- 人間への確認を促す
- ADR を残す

といったガードレールにある。

### 仮説4

高性能モデルは実装ではなく、

- 要件整理
- 不明点抽出
- 設計判断
- レビュー

で利用した方が費用対効果が高い。

## ゴール

AI 駆動開発において、

- どのモデルを使うべきか
- どの程度ルールを書くべきか
- どの工程で高性能モデルを利用すべきか

をデータに基づいて判断できるようにする。
