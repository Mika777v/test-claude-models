# 評価の方針

> **目的**: このリポジトリでの測り方の枠組み。測定を始める前に読み、決めたいことと「どんな結果なら、どう決めるか」をここに沿って書く。
> **いつ読むか**: 新しい測定（Task・条件）を考えるとき。結果を読むとき。
> **元**: 2026-11-06 にオーナーと話した下書き（ai-driven-dev-template の `bench/agent-bench` の `tools/agent-bench/EVALUATION-draft.md`）。この文書を変える PR は「確認が必要な項目」（`AGENTS.md` §3-4）。
> これまでの結果は [`bench/results/`](../bench/results/) の各 README、道具の使い方は [`bench/README.md`](../bench/README.md)、進み具合は [`PROGRESS.md`](PROGRESS.md)、決めた理由は [`adr/`](adr/README.md)。

## 1. 決めたいことから始める

1つの測定は、オーナーが決めたいこと1つに対応させる。測る前に「どんな結果なら、どう決めるか」を書く。
（例: 要件の段階で②の境目を確認に回す率が上がり、費用が2倍以下なら、Epic の始めに入れる）

| 決めたいこと | これまでの測定 | わかったこと |
|---|---|---|
| ルールをどこまで入れるか | T0〜T3（ルールあり・なし・案内なし） | 正しさは変わらない。変わるのは、人の確認に回すこと・形・文書 |
| どのモデルをどこに使うか | T3・T4（モデルを変える） | 正しさはモデルで変わらない。ルールを守る度合いと費用が変わる |
| 要件を詰める段階を入れるか | T4・T5（要件の段階。Opus・Sonnet） | 揺れが消え、境目がオーナーへの質問になる。費用は 2〜5倍。確認に回すだけなら、確認の項目に「業務の決まりを足す・変える」を足せば要件の段階なしでも 3/3（T5-biz） |
| 文書を残す価値はあるか | T2（続きの作業） | 後の AI は、残った物（前の PR の本文・文書）を真似る |
| ルールはどこに書けば効くか | T4（bare / none）・R1 | 作業の途中で読む文書に書けば効く。R1 でも、ADR に書いた「確認する」はルールが無くても守られ（3/3）、CLAUDE.md の後ろの「教科書を書く」は守られなかった（0/3） |

## 2. 変えるもの・そろえるもの

- 変えるもの（1回の測定で1つか2つ）: ルールの量・モデル・担当の分け方（要件・実装・レビュー）・前の作業が残した物
- そろえるもの: 土台のコミット・AI への指示・使ってよい道具・1回の上限の金額・モデル（比べないとき）

## 3. Task の2つの軸

| | あいまいさ無し | ①言葉の意味・目的 | ②業務の決まり・境目 | ③範囲 |
|---|---|---|---|---|
| 影響度: 低 | T0 | | | |
| 影響度: 中 | T1・T2 | | T5 | |
| 影響度: 高（スキーマ） | T3 | T4（①と②が混ざる） | | |

- 1つの Task に、あいまいさは1種類だけ入れる
- あいまいさの種類（T4 で Opus が出した質問から分けた）:
  - ① 言葉の意味・目的（オーナーが決める。戻しにくい）
  - ② 業務の決まり・境目（オーナーが決める。戻しにくい。依頼の文から一番見えにくい）
  - ③ 範囲（オーナー。AI の案で足りることが多い。戻しやすい）
  - ④ 見せ方・言葉（どちらでも。戻しやすい）
  - ⑤ 作り方（AI が決めて ADR に書く）

## 4. 測るもの（指標）

| 種類 | 何を見るか | 測り方 | 注意 |
|---|---|---|---|
| 正しさ | 隠した受け入れテスト・型・lint | 自動 | 曖昧な Task では差が出ない。受け入れテストは、あいまいにした点の正解を決めない（どう決めても守るべきことだけ見る） |
| 人の手間 | 確認が必要な項目に挙げたか・形・文書の更新・直し漏れ | 自動＋読む | 自動の判定はよく外れた（選択肢から外したか・直し漏れ・範囲外・「なし（スキーマは変えていない）」を申告と数える） |
| 判断 | 境目に気づいたか・どう決めたか・聞いたか・決めたことを書いたか | 読む | **Task ごとに、測る前にチェック項目を決める**（[T5](../bench/results/2026-11-06-T5/README.md) の (a)〜(d) のように） |
| 費用 | トークン・金額・時間 | 自動 | 1つの測定で使ってよい量を先に決める（利用枠の上限に当たったことがある） |

## 5. 回数と書き方

- 1つの条件で最低3回。「3回中2回」のように書く。割れたら増やす
- 平均だけでなく幅も書く
- 1回だけの読みは、3回で変わることがある（T4 の「ルールのある Sonnet が聞く」は 1/3 だった）

## 6. 1つの測定の流れ

1. 決めたいことと、「この結果ならこう決める」を書く（Issue 1つ）
2. Task・条件・判断のチェック項目・使ってよい量を決める
3. dry で、受け入れテストと落とし穴が効くかを確かめる
4. 動かす（3回）
5. 自動で採点し、チェック項目に沿って読む
6. 結果の README に書き、決めたことを（必要ならテンプレートに）反映する

## 7. 正解をどう持たせるか（[ADR-0003](adr/0003-tasks-from-routepense-prs.md) で決めた）

> 決定: routepense の過去の PR をやり直す Task（`R*`）を主にし、実際にマージした結果（テスト・PR の本文）を正解にする。
> 選ぶときの注意（R1 から）: Issue の「確認が必要な項目」を外しても、土台の ADR・PROGRESS.md に同じ答えや作り方が書いてあることがある。現実に近いのでそのままでよいが、「AI が自分で気づくか」を見る Task では、土台の文書に答えが無い PR を選び、`config.sh` に土台のどこに何が書いてあるかを残す。

> 決めたら ADR に書き、この節はその要点とリンクにする。

「正解」は指標ごとに意味が違う。

- 正しさの正解: 隠した受け入れテスト
- 判断の正解: **オーナーの答え**（あいまいにした点を、オーナーならどう決めるか）。どのリポジトリにも無いので、オーナーが書くしかない
- 人の手間の正解: ルールの一覧（確認が必要な項目など）

Task の作り方の案:

- A. 既にあるリポジトリの過去の PR から選ぶ（PR の前のコミットが土台、PR のテストが受け入れテスト）。現実的で数を作りやすい。公開の OSS は学習データに入っている恐れがあり、決まりもテンプレートと違う
- B. 一から作る。あいまいさの種類・落とし穴・オーナーの答えを狙って作れる。手間がかかり、作り物になる
- おすすめ（下書き時点）: routepense を題材に続ける。はっきりした Task は routepense の過去の Task（Issue と、マージした PR とテスト）から選ぶ。あいまいな Task は、それを元にあいまいにした版を作り、オーナーが「オーナーの答え」を書く

## 8. いまの測り方で測れないもの

- オーナーが答える場面（「オーナーの答え」のファイルを渡せば近いものを測れる。おすすめと違う答えにすれば、従うかも見られる）
- 大きい作業・長い作業（Epic のように何 PR にもわたるもの）
- routepense 以外での一般性
