# ADR-0002: 測定の土台を routepense の固定コミットにし、条件は「ルールの文書を消す量」で分ける

- 状態: 決定（これまでの測定でそうしてきたことを、2026-11-06 に記録した）
- 日付: 2026-11-06
- 関係する Issue・PR: ai-driven-dev-template の [#7](https://github.com/Mika777v/ai-driven-dev-template/pull/7)〜[#10](https://github.com/Mika777v/ai-driven-dev-template/pull/10)（結果の表）

## 背景

運用ルールの効果を比べるには、ルール以外のもの（コード・指示・道具・モデル）をそろえる必要がある。
また、作り物のリポジトリでは、DB の作り直しのような実際の落とし穴が出にくい。

## 選択肢

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A | 実際に運用中のリポジトリ（routepense）の固定コミットを土台にし、ルールの文書を消して条件を作る | 実際の落とし穴があり、テンプレートのルールがそのまま入っている | routepense 以外での一般性はわからない |
| B | ベンチ用に小さなリポジトリを作る | 狙った落とし穴を入れやすい | 作り物になり、ルールの文書も作り直しになる |
| C | 公開の OSS の過去の PR を使う | 数を作りやすい | 学習データに入っている恐れ。決まりがテンプレートと違う |

## 決定

A。

- 土台: routepense の固定コミット（`41ac314`、T4 以降は `d4d15fd`）。`BENCH_BASE` で指定する
- 条件（`BENCH_CONDITIONS`）は、ルールの文書を消す量で分ける: `template`（そのまま）→ `minimal`（CLAUDE.md を説明・技術スタック・コマンドだけに）→ `bare`（運用ルールの文書・PR / Issue のテンプレートも消す）→ `none`（ADR を書くときのルールも消す）。続きの Task は `from-<前の条件>`
- AI への指示は、どの条件でも同じにする。運用のルールのことは書かない（ルールの文書を自分で読むかを見るため）
- 作業場所は毎回まっさら（git の履歴は1コミット）。GitHub にはつながず、PR の文面はファイルに書かせる
- 利用枠の上限で止まった回は採点せず、結果に残さない（やり直す）

## 理由

ルールの効果は「実際に起きる落とし穴をどう扱うか」に出るため、本物のリポジトリを土台にした。条件を「消す量」の1軸にすると、どの文書が効いているかを順に切り分けられる（T4 で `bare` と `none` の差から、ADR の README が ADR を書かせていたとわかった）。

## 影響

- 結果は routepense での結果で、ほかのリポジトリでの一般性は測れていない（`docs/EVALUATION.md` §8）
- 土台のコミットを変えたら、前の結果とは直接比べない（結果の README に土台を書く）
- Task の作り方（過去の PR から選ぶか・一から作るか）は未決（`docs/EVALUATION.md` §7）。決めたら新しい ADR に書く
