# ADR-0004: 評価の指標を「正しさの関門 ＋ 品質の点 Q ÷ 成功1回あたりのコスト」にし、Task は難しさの段ごとにまとめる

- 状態: 決定（2026-11-06 にオーナーと会話で決めた）
- 日付: 2026-11-06
- 関係する Issue・PR: このADR の PR

## 背景

オーナーは「Y = 品質 ÷ コスト（消費コンテキスト量）」を指標の案にした。品質には、テストの通過率・Linter のエラー数・複雑度を考えていた。
一方、これまでの測定（T0〜T5・R1）では、正しさ（受け入れテスト）は条件によらずほぼ満点で、差が出たのは「確認に回すか」「オーナーと同じに決めるか」「形・文書」だった。
テストの通過率と Linter だけで品質を作ると、Y はほぼコストの逆数になり、「ルールが無いのがいちばん良い」と出る。

## 選択肢

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A | Y = 品質 ÷ コスト（品質 = テスト・Linter・複雑度） | 1つの数で比べられる | 安くて間違った作りが高く出る。差の出ている軸（申告・判断）が入らない。複雑度は向きがはっきりしない（入力を丁寧に確かめるほど悪くなる） |
| B | 正しさを関門にし、品質の残りを点 Q にして、成功1回あたりのコストで割る | 正しくない作りを除ける。差の出る軸が入る | 重みを決める必要がある |
| C | 1つの数にせず、軸を並べるだけ | 読み違いが少ない | 決めるときにまとめにくい |

## 決定

B。ただし表には、Y と並べて軸ごとの値も出す（C の良い点を残す）。

```
関門: 正しさ = Task に書いてあることの受け入れテスト（config.sh の ACCEPTANCE）が全部通り、型チェック・lint が通る
       通らない回は「失敗」。成功率に数える

Y = Q ÷ 成功1回あたりのコスト
    成功1回あたりのコスト = 1回の平均のコスト ÷ 成功率
    Q（0〜1）= 0.4 × 決め方 ＋ 0.4 × 申告 ＋ 0.2 × 形・文書   （成功した回の平均）
```

- **決め方**: Task に無く、実際の PR でオーナーが決めたことのテスト（config.sh の `DECISION`）の通過率。R1 は分けていない（R2 から分ける）
- **申告**（確認が必要な項目）
  - 確認が要る Task: 決まった節に書いた = 1、確認が要るとは書いたが節の外 = 0.5、書かない = 0
  - 確認が要らない Task: 「なし」= 1、要らないことを確認に回した = 0.5（オーナーの手間が増え、自動マージが止まる）
- **形・文書**: ブランチ・コミット・PR のタイトル・PR の見出し・その Task で要る文書の更新（教科書など）のうち、できた割合
- **重み**（0.4・0.4・0.2）は初めの値。測定ごとに「決めたいこと」に合わせてオーナーが変えてよい（Issue に書く）
- **コスト**は2つ出し、決めたいことに合うほうを分母にする
  - ドル（モデルを比べるとき。単価がモデルごとに違う）
  - 入力トークン（キャッシュの読み出しを含む。ルールの文書の長さを比べるとき）
- **参考値**（Y には入れない）: 実際の PR と比べた差分の大きさ（AI の行数 ÷ 実際の行数）。1.5倍を超えたら「やりすぎ」の印。複雑度（Cyclomatic Complexity）は使わない

**難しさ**（実現しようとしているものの複雑さ）は Y に掛けない。

- 同じ Task の中で条件を比べるときは、難しさはどの条件でも同じなので要らない
- Task をまたいでまとめるときは、Task を **易・中・難** の段に分け、段ごとに Y を並べる。段は config.sh に書く
  - 決め方: オーナーの見積り（Issue）・あいまいさの数（決め方のテストの数）・土台の文書に作り方や答えがあるか
  - 測った成功率が段と合わなければ（易のはずが成功率が低いなど）、測った結果で段を直す

## 理由

- 決めたいこと（どのルール・どのモデルを使うか）には「正しいことを前提に、人の手間とお金がどう変わるか」が効く。正しさを割り算に入れると、半分しか動かない作りと動く作りが同点になりうる
- 差が出ている軸（申告・決め方・形）を Q に入れると、R1 で template が守っていたもの（申告の場所・形）が点に出る（試算: bare 3.4・minimal 3.3・template 4.2）
- 難しさは1つの数にしにくく、R1 のように土台の文書しだいで変わる。段に分けて並べるほうが、読み違いが少ない

## 影響

- `score.sh` は、正しさ（`accept_*`）と決め方（`decision_*`）を分けて数える（config.sh の `DECISION`）
- まだ無いもの（次の PR で足す）: 採点の JSON での出力・トークンの内訳（入力・出力・キャッシュの作成・読み出し）・Q と Y の計算・差分の大きさの比
- 重みを変えたら、表に書いた Y は比べられなくなる。重みは結果の README に必ず書く
- 申告の点の付け方は、自動の `pr_confirm_declared` ではなく、PR の本文を読んで付ける（自動の判定はよく外れる。AGENTS.md §6）
