# ADR-0003: Task を routepense の過去の PR から作り、実際にマージした結果を正解にする

- 状態: 提案（オーナーの確認待ち）
- 日付: 2026-11-06
- 関係する Issue・PR: 測定 A の Issue（この ADR の PR に書く）・`docs/EVALUATION.md` §7

## 背景

`EVALUATION.md` §7 で「正解をどう持たせるか」が未決だった。これまでの Task（T0〜T5）は一から作ったもので、作るのに手間がかかり、数が増えない。
オーナーの方針は「routepense の今を正解にして、仮説を確かめる」。routepense には、Issue → PR → テスト付きでマージした機能の PR が約25ある。

## 選択肢

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A | 過去の PR をやり直す（1→10）。土台は PR の1つ前のコミット、Task は Issue の本文、受け入れテストは PR で足されたテスト | Task を数多く作れる。正しさ・判断・申告の正解がすべて実物（テスト・差分・PR の本文） | テストが実際の作りに寄る（関数名など）。AI が学習で routepense を見ている恐れは小さい（非公開に近い個人のリポジトリ）が、ゼロではない |
| B | 要件定義から一から作る（0→1）。今の routepense のテスト一式で採点 | 仮説1（0→1 のコスト）を直接測れる | 1回が大きい（推定 $5〜25・数時間）。途中で止まると比べられない |
| C | 一から作る Task を続ける | あいまいさ・落とし穴を狙って作れる | 手間がかかり、作り物になる |

## 決定

A を主にする。B は1つの Epic で小さく試してから決める。C は、狙った場面（あいまいさの種類など）を作りたいときだけ使う。

A の作り方:

- **名前**: `R<番号>-<内容>`。`config.sh` の `TASK_BASE` に土台（PR の1つ前のコミット）を書く。`run.sh` と `dry-all.sh` はそれを使う
- **Task の本文**: Issue の本文から、次を外す
  - 「確認が必要な項目」の欄（AI が自分で気づくかを見るため。正解は実際の PR の本文に残っている）
  - 親 Epic・前提（「#57 のマージの後に」など）・教科書の決まりのような、その時の運用の行は、Task の中身に関係しなければ外す
- **受け入れテスト**: PR で足された `it(...)` を、土台にある関数・API だけを使うものに限って、そのまま `*.acceptance.test.ts` に移す。テストの中身は変えない
  - Issue に書いてなく、PR（オーナー）が決めたことを確かめるテストは、`config.sh` に「決めたこと」として書く。正しさではなく「オーナーと同じに決めたか」として読む
  - 土台でも通ってしまうテスト（前からの動きを守るもの）も、`config.sh` に書いておく
  - 土台に無い関数名・ファイル名に頼るテストしか無い PR は選ばない（Issue に名前が書いてあれば使ってよい）
- **正解の実装**: `reference.patch` は実際の PR の差分そのもの
- **申告の正解**: 実際の PR の本文の「確認が必要な項目」。`CONFIRM_RE` に合わせる。「なし」が正解の Task も入れ、確認に回しすぎないかも見る

## 理由

- オーナーが決めたい「routepense の今を正解に」に、いちばん素直に合う
- 1つの Task を数十分で作れる（R1 で確かめた）。数をそろえやすく、「3回中2回」のような読みを Task をまたいで重ねられる
- 正しさのテストと、オーナーの決め方（Issue に無いこと）を分けて読める。これまで「オーナーの答え」が無くて測れなかった判断の正解が、実際の PR から取れる

## 影響

- `run.sh`・`dry-all.sh` が `TASK_BASE` を読む。土台が Task ごとに違うので、作業の置き場所（`BENCH_OUT`）も土台ごとに分かれる（dry-all は自動）
- 土台が古いと、その時の運用ルール（長い CLAUDE.md など）で測ることになる。条件（template / bare など）の中身が Task ごとに少し違う。ルールの版をそろえて比べたいときは、今のルールの文書を差し替える条件を足す
- PR のテストが実際の作りに寄りすぎて、別の正しい作りを落とすことが続いたら、受け入れテストを API の外から見るものに書き直すかを考え直す
