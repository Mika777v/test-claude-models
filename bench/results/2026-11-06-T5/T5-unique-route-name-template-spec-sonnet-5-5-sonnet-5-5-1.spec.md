# SPEC: 同じ名前のルートを登録できないようにする

## 1. 調べて分かったこと

- `POST /api/routes`（`backend/src/routes/route-router.ts`）は `parseRouteInput` で検証し、通れば `repo.create` で保存する。名前の重複は見ていない。
- `parseRouteInput` の `text()`（`backend/src/validation/fields.ts`）は、名前の前後の空白を取り除いた値を返す。
- `routes` テーブル（`backend/src/db/migrations.ts` の version 1・3）に、名前の UNIQUE 制約は無い。
- `RouteRepository`（`route-repository.ts`）に、名前でルートを探す窓口は無い。`list(userId)` で全件を取れる。
- 画面（`frontend/src/routes/RouteForm.tsx`）は、失敗した応答の `fieldErrors` を `toRouteFormErrors` で欄ごとに分け、`field: "name"` の文をルート名の欄の下に出す。HTTP のステータスは見ていない。`frontend/src/api-client.ts` も、`!res.ok` なら本文を `ApiError` として返す。**409 でも、本文が同じ形なら、画面側のコードはたぶん変えずに表示できる。** 実装する人は確かめ、テストで固定する。
- 登録済みのルートに、すでに同名のものがあっても、記録（`daily_records`）は名前をコピーして持つので壊れない（要件定義 §5）。
- `docs/api/openapi.yaml` の `POST /api/routes` に、409 の記述が無い。`docs/troubleshooting.md` の「API のステータス」の表にも 409 が無い。

## 2. オーナーに確かめること（あいまいな点）

| # | 確かめること | 選択肢 | おすすめ | 理由 |
|---|---|---|---|---|
| Q1 | 編集（`PUT /api/routes/:id`）で、別のルートと同じ名前に変えるのはどうするか | A. 今回は登録だけ。編集は別 Task で扱う / B. 編集でも 409（自分自身は除く）にする | **A** | Task の「作業内容」は登録だけで、受け入れ条件にも「編集は今までどおり」とある。ただし A のままだと、**編集で同じ名前を作れてしまい、困りごと（どちらか分からない）が残る**。B は小さな変更なので、続きの Task を早めに作ることを勧める |
| Q2 | 「同じ名前」の見分け方 | A. 前後の空白を取った後の完全一致 / B. 全角半角・大文字小文字も同じとみなす（正規化） / C. 取る前の文字列で比べる | **A** | `text()` がすでに前後の空白を取るので、保存される値どうしを比べるのが最も単純で、画面で見える違いと合う。「自宅↔本社」と「自宅<->本社」のような見た目の違いは、利用者が見分けられるので止めなくてよい。B は規則が増え、止める理由の説明も難しくなる |
| Q3 | DB にも UNIQUE を付けるか（`user_id, name`） | A. 付けない。API で確かめるだけ / B. 新しい migration で UNIQUE インデックスを足す | **A** | 利用者は1人で、同時に登録する競合は実質起きない。B は**すでに同名のルートがある DB で migration が失敗する**（今回の困りごとがまさにそれ）。直すには既存データの整理が先に要り、戻しにくい変更（DB のスキーマ。オーナー確認の PR と ADR が要る）になる。今回の範囲を超える |
| Q4 | すでにある同名のルートはどうするか | A. 何もしない（利用者が画面で名前を直す/消す）/ B. migration で自動で名前を変える | **A** | 自動で名前を書き換えると、利用者の意図しない変更になる。Q1 の A なら、編集で名前を直すことはできる（今の編集は同名でも通るので、自分で直せる） |
| Q5 | 検証の順番（形式の誤りと重複が両方あるとき） | A. 形式の誤りを先に 400 で返し、通ったら重複を見る / B. 重複を先に見る | **A** | 名前が空・長すぎる値は、重複を比べる意味が無い。今の 400 の動きも変わらない |
| Q6 | 409 の本文の `error` の文 | A. 400 と同じ「入力に誤りがあります」/ B. 「同じ名前のルートがあります」 | **A** | Task の指定は「今のエラーと同じ形」。画面は `fieldErrors` があるとき `error` を使わず、欄の文だけを出すので、どちらでも見た目は同じ。400 とそろえる。`fieldErrors[0]` は `{ field: "name", message: "同じ名前のルートがあります" }` |

以降の要件は、おすすめ（Q1=A、Q2=A、Q3=A、Q4=A、Q5=A、Q6=A）が通ったものとして書く。

## 3. 要件

### やること

1. **backend: 重複の確認**
   - `RouteRepository` に、名前でルートがあるか確かめる窓口を足す（例: `existsByName(userId, name): boolean`、または `findByName`）。実装は `SqliteRouteRepository`。比べるのは同じ `userId` のルートの `name`（完全一致）。
   - `POST /api/routes` で、`parseRouteInput` が成功した後、同名のルートがあれば `repo.create` を呼ばずに **409** を返す。
   - 本文:
     ```json
     { "error": "入力に誤りがあります", "fieldErrors": [{ "field": "name", "message": "同じ名前のルートがあります" }] }
     ```
     型は `ApiError`（`shared/src/api.ts`）のまま。型や `shared/` は変えない。
   - 「同じ名前のルートがあります」の文は、router の中の定数にして、テストと画面で同じ文を確かめられるようにする。
2. **画面**
   - ルートの登録フォームで 409 が返ったとき、「同じ名前のルートがあります」をルート名の欄の下に、今の入力の誤りと同じ出し方（`field-error`・`aria-describedby`）で出す。
   - 今のコードで足りるはず（上の「調べて分かったこと」）。足りなければ最小限だけ直す。足りていても、**409 の応答で欄の下に出ることのテストを足す**（`route-form.test.ts` か RouteForm のテスト）。
3. **API の仕様書**: `docs/api/openapi.yaml` の `POST /api/routes` に `"409"` を足す（本文は `ApiError`、例は上の JSON）。`BadRequest` と同じように `components/responses` に置いてもよい。
4. **トラブルシュート**: `docs/troubleshooting.md` を同じ PR で直す（CLAUDE.md の決まり）。
   - 「API のステータス」の表に 409 の行を足す（同名のルートがある。`backend/src/routes/route-router.ts`）。
   - 画面のメッセージの表に「同じ名前のルートがあります」（欄の下の赤い文。409）の行を足す。
5. **テスト**（Vitest）
   - `route-router.test.ts`: 同名で登録すると 409・本文が上のとおり・一覧の件数が増えない／違う名前なら 201／前後に空白のある同名（`" 自宅↔本社 "`）も 409／形式の誤りは今までどおり 400（重複より先）。
   - `sqlite-route-repository.test.ts`: 名前の確認の窓口（ある・無い・別の `userId` のルートは数えない）。
   - 画面のテスト: 上の 2。

### やらないこと

- 編集（`PUT`）での重複の確認（Q1。別 Task にする）。
- DB のスキーマ変更・UNIQUE インデックス・migration（Q3）。
- すでにある同名のルートの自動の整理・名前の変更（Q4）。
- 全角半角・大文字小文字をそろえた比較（Q2）。
- 画面での事前の確認（登録前に一覧と見比べる）。API の応答だけで足りる（検証は入力の境界で行う方針）。
- 一覧・削除・日次記録・一括設定・CSV の変更。

### 受け入れ条件

- [ ] すでにある名前でルートを登録しようとすると 409 で、本文は上のとおり。`GET /api/routes` の件数は増えない
- [ ] 違う名前なら、今までどおり 201 で登録できる
- [ ] 前後の空白だけが違う名前も「同じ」として 409 になる
- [ ] 名前が空などの形式の誤りは、今までどおり 400
- [ ] 画面で同名を登録すると、「同じ名前のルートがあります」がルート名の欄の下に出て、ルートは増えない。ほかの欄の入力は消えない
- [ ] ルートの一覧・編集・削除・出勤の保存など、今までの動きは変わらない（既存のテストが通る）
- [ ] `docs/api/openapi.yaml`（`openapi.test.ts` が通る）と `docs/troubleshooting.md` を直した
- [ ] `npm run typecheck && npm run lint && npm run test` が通る

## 4. 戻しにくい変更・進め方

- **DB のスキーマ・要件定義の変更は不要**（Q3=A のため）。ADR も不要。
  - ただし要件定義 F1 には「ルート名は重複しない」と書かれていない。入れるかはオーナーに任せる（入れるなら要件定義の変更で、オーナー確認の PR になる。この Task の PR に混ぜず、別 PR にする）。
- Q3 で B（UNIQUE インデックス）を選ぶ場合は、戻しにくい変更になる。その場合は ADR を書き、スキーマの PR として自動マージせずにオーナーが確認する。既存の同名データの扱い（Q4）を先に決めること。
- 409 は新しいステータスなので、API を使う側（画面）にとっては追加の挙動。ただし本文の形は変わらないので、後ろ向きの互換性の問題は無い。
- 1ブランチ・1 PR・`Closes #Task`。PR のタイトルは Conventional Commits。
