## 1. あいまいなところ・オーナーに確かめること

### Q1. 編集（`PUT /api/routes/:id`）でも、ほかのルートと同じ名前に変えるのを止めるか

Task は「登録（POST）」だけを書き、受け入れ条件には「編集…今までの動きは変わらない」とある。しかし編集で名前を変えれば、同じ重なりがまた作れてしまい、Task の目的（出勤を選ぶときに見分けられる）が守れない。

| 選択肢 | 内容 |
|---|---|
| A | 登録（POST）だけ止める。編集は今のまま（Task の文のとおり） |
| **B（おすすめ）** | 編集でも、**名前を変えて**ほかのルートと同じになるなら 409。名前を変えない編集（運賃だけ直すなど）は、今すでに重なっているルートでも通す |
| C | 編集では、名前を変えたかどうかにかかわらず、ほかのルートと同じ名前なら 409 |

- **おすすめ: B**
- 理由: A だと編集で抜け道が残り、目的が守れない。C だと、すでに2件ある「自宅↔本社」は、名前を変えないかぎり運賃も直せなくなり、「今までの動きは変わらない」に大きく反する。B なら抜け道をふさぎつつ、今あるデータの編集は今までどおりにできる
- 影響: 受け入れ条件の3つ目の「編集は変わらない」は、「ほかのルートと同じ名前に**変える**編集だけは 409 になる」という例外つきになる（§3 に書いた）

### Q2. 「同じ名前」をどう比べるか

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 前後の空白を取り除いた後の、文字列の完全一致（今の `trim()` のまま） |
| B | A に加えて、大文字と小文字・全角と半角などをそろえて比べる（Unicode の NFKC など） |
| C | B に加えて、記号の違い（`↔` と `<->`、`-` と `ー` など）も同じとみなす |

- **おすすめ: A**
- 理由: 困ったのは見た目がまったく同じ名前で、A で防げる。B・C は「どこまで同じとみなすか」の決まりが増え、利用者から見て「なぜ弾かれたか」が分かりにくい。保存する名前と比べる名前が食い違う心配も無い。必要になれば後から B に広げられる（狭いほうから広げるのは、今あるデータを壊さない）
- 影響: `"自宅↔本社"` と `" 自宅↔本社 "` は同じ（trim されるため）。`"自宅↔本社"` と `"自宅<->本社"`、`"Home"` と `"home"` は別の名前として登録できる

### Q3. すでに重なっている「自宅↔本社」の2件をどうするか

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | データには手を付けない。オーナーが画面の編集で片方の名前を変える（例: 「自宅↔本社（バス）」） |
| B | マイグレーションで自動で名前を変える（例: 2件目に「(2)」を付ける） |
| C | 起動するときや一覧で、重なりを警告する |

- **おすすめ: A**
- 理由: 2件のどちらをどう呼ぶかは持ち主にしか分からない。B はデータを書き換える戻しにくい変更で、名前は日次記録にもコピーされている（ただし過去の記録のコピーは変わらない）ので、どれが元のルートか余計に分かりにくくなる。個人利用で件数も少なく、手で直すほうが確実
- 影響: Q1 で B を選べば、名前を変えない編集・削除・出勤の保存は今の2件でも今までどおりできる。今のデータのままでもアプリは動く

### Q4. DB に一意の制約（`UNIQUE (user_id, name)`）を張るか

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 張らない。API（受け口）で「同じ名前があるか」を調べてから登録・編集する |
| B | 新しいマイグレーション（version 4）で `CREATE UNIQUE INDEX` を張り、制約違反を 409 に変える |

- **おすすめ: A**
- 理由:
  - 今のデータに重なりがあるので、B のマイグレーションはそのままでは失敗する。先にデータを直すマイグレーション（Q3 の B）が要り、戻しにくい変更が2つ重なる
  - 個人利用・1プロセスで、`node:sqlite` は同期で動く（ADR-0001）。調べてから登録するまでの間に、別のリクエストが割り込むことは無い（Express のハンドラーの中で `await` を挟まないかぎり）。画面の「登録する」も送信中は押せない
  - CLAUDE.md の方針「バリデーションは入力の境界（APIの受け口）で行う」に合う
  - 複数ユーザーや複数プロセスにする時（スコープ外）に、改めて制約を張ればよい
- 影響: **DB のスキーマは変えない。** マイグレーションも足さない。B を選ぶなら、DB のスキーマの変更・データの移し方として ADR を書き、PR は自動マージせずオーナーの確認を取る

### Q5. 409 の本文の `error`（全体の文）を何にするか

Task は「本文は今のエラーと同じ形（`error` と `fieldErrors`）」「`fieldErrors` の文は『同じ名前のルートがあります』」とし、`error` の文は決めていない。

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | `error` も `"同じ名前のルートがあります"` |
| B | `error` は 400 と同じ `"入力に誤りがあります"` |

- **おすすめ: A**
- 理由: 開発者ツールや `curl` で `error` だけを見ても、400（形の誤り）と 409（ほかのルートとの重なり）を見分けられる。`docs/troubleshooting.md` の表でも行を分けられる。画面では `fieldErrors` があると上の赤い枠に `error` は出ない（`RouteForm.tsx`）ので、どちらでも画面の見え方は同じ
- 影響: 本文は `{ "error": "同じ名前のルートがあります", "fieldErrors": [{ "field": "name", "message": "同じ名前のルートがあります" }] }`

### Q6. 要件定義（`docs/requirements.md`）をどう直すか・PR をどう分けるか

「同じ名前のルートは登録できない」は新しい要件の決まりなので、要件定義に書く必要がある。要件定義の変更は自動マージしない決まり（CLAUDE.md・`docs/DEV_RULES.md`）。

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 実装と同じ PR で `requirements.md` を直し、PR は自動マージせず、本文の「確認が必要な項目」に書く |
| B | 要件定義の変更だけを先に別の PR にし、オーナーがマージしてから実装の PR を作る（実装の PR は自動マージ） |

- **おすすめ: A**
- 理由: 「1つの作業 = 1 PR」の決まりに合う。オーナーはこの SPEC の質問に答えた時点で中身を決めているので、確認は1回で済む。差分も小さい
- 影響: PR に `needs-confirm` 相当の扱い（自動マージを予約しない）が要る

### Q7（確認だけ）. 消したルートの名前を、もう一度使えるか

- **おすすめ: 使える。** ルートの削除は行ごと消す（物理削除）ので、比べる相手に入らない。消したルートを使っていた日次記録には同じ名前のコピーが残るが、記録の名前は比べない（記録はその時点のコピーで、U7 の決まりどおり）
- 実装は何もしなくてよい（`routes` テーブルだけを調べれば自然にそうなる）。テストで確かめる

## 2. やること（おすすめの答えを採用した要件）

### 2.1 API の決まり

1. **`POST /api/routes`**
   - 今の検証（`parseRouteInput`）を先に行う。誤りがあれば今までどおり 400（名前が重なっていても 400 を優先する）
   - 検証が通ったら、**同じユーザーの**ルートに、trim 後の名前が完全に同じものがあるか調べる
   - あれば、登録せずに **409** で次の本文を返す
     ```json
     { "error": "同じ名前のルートがあります",
       "fieldErrors": [{ "field": "name", "message": "同じ名前のルートがあります" }] }
     ```
   - 無ければ今までどおり 201
2. **`PUT /api/routes/:id`**（Q1 の B）
   - 今の検証を先に行う（400）
   - 対象のルートが無ければ今までどおり 404（404 を 409 より先に判定する）
   - **新しい名前が今の名前と違い**、かつ自分以外の同じユーザーのルートに同じ名前があれば、更新せずに 409（本文は POST と同じ）
   - それ以外（名前を変えない、または重ならない名前に変える）は今までどおり 200
3. `GET`・`DELETE`・日次記録・一括設定・追加の移動の API は変えない

### 2.2 backend の作り

- `RouteRepository` に、名前で探すメソッドを1つ足す（例: `findByName(userId: string, name: string): Route[]`。重なっている今のデータがあるので、1件ではなく配列で返すか、`excludeId` を受け取って「ほかに同じ名前があるか」を返す形にする。名前・形は実装する人が決めてよい）
- `SqliteRouteRepository` で実装する（`SELECT … FROM routes WHERE user_id = ? AND name = ?`）。索引は足さない（件数が少なく、`routes_user_id` で足りる）
- 重なりの判定は `route-router.ts` で行う（受け口の判定。`parseRouteInput` は本文だけを見る純粋な関数のまま残し、DB を見る判定を混ぜない）
- 409 の本文を作るところは、POST と PUT で同じ値を使う（`notFound` と同じように定数にする）
- 調べてから登録・更新するまでの間に `await` を挟まない（Q4 の前提）。今のハンドラーは同期なので、そのまま書けばよい
- 文の「同じ名前のルートがあります」は1か所に置く

### 2.3 frontend

- **コードの変更は要らない見込み。** 409 でも `fieldErrors` の `field: "name"` が `toRouteFormErrors` で `byField.name` に入り、「ルート名」の欄の下に赤い文が出る。`aria-invalid` と `aria-describedby` も今の仕組みで付く。入力した値は消えない。上の赤い枠は出ない
- 実際に画面で、登録と編集の両方で確かめる（`/run` などで動かす）
- 動かして食い違いがあれば、最小の修正をする（その場合は PR の本文に書く）

## 3. 受け入れ条件

- [ ] 編集で、ほかのルートと同じ名前に変えようとすると 409 で、ルートは変わらない（Q1）

- [ ] 消したルートの名前で、新しいルートを登録できる
- [ ] 画面のルートの登録のフォームで、重なる名前を登録すると「同じ名前のルートがあります」が「ルート名」の欄の下に、今の入力の誤りと同じ出し方で出る。入力した値は消えない。編集のフォームでも同じ
- [ ] ルートの一覧・名前を変えない編集・削除・出勤の保存・一括設定・追加の移動・CSV など、ほかの動きは変わらない（今のテストがすべて通る）

- [ ] `npm run typecheck && npm run lint && npm run test` が通る

## 4. やらないこと

- DB のスキーマの変更（一意の制約・索引・マイグレーションの追加）（Q4）
- 今すでに重なっているルートのデータの書き換え・自動の名前の付け直し・警告の表示（Q3）
- 大文字と小文字・全角と半角・記号の違いをそろえて比べること（Q2）
- 画面で、送る前に名前の重なりを調べる（入力しながらの判定）。判定は API だけで行う
- 出勤の選択肢・追加の移動の「ルートから選ぶ」の表示を変える（出発地・到着地を添えるなど）
- 日次記録にコピーしたルート名の重なりの扱い
- ADR（Q4 で B を選んだときだけ要る）

## 5. 戻しにくい変更があるか

- **DB のスキーマ: 変えない**（おすすめの答えのとき）。Q4 で B を選ぶと、マイグレーションの追加と既存データの書き換えが要り、ADR とオーナーの確認が要る
- **要件定義の変更: ある**（F1・§5・決定の記録 U11）。自動マージせず、オーナーが確かめてからマージする
- **API の形: 409 を足す。** 今のクライアント（この frontend だけ）は `ApiError` の本文をステータスにかかわらず扱うので壊れない。後から外す・別の番号にするのは容易
