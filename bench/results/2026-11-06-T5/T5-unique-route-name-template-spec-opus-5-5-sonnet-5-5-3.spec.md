# SPEC: 同じ名前のルートを登録できないようにする

> 実装する人に渡す要件。オーナーへの確認はこの後で行うので、下の「確かめること」は **おすすめの答えを採用したもの** として要件を書いている。オーナーの答えが違ったら、該当する節を直してから実装する。

## 1. 背景と今の作り（調べた結果）

- ルートの一覧に「自宅↔本社」が2つあり、出勤のルートを選ぶとき（日の編集パネル・一括設定・追加の移動）に見分けられなくなった。
- 今は、どこにも名前の重複の確認が無い。
  - DB: `routes` テーブル（`backend/src/db/migrations.ts` の version 1・3）に `name` の UNIQUE は無い。インデックスは `routes_user_id` だけ。
  - API: `backend/src/routes/route-router.ts` の `POST /` は `parseRouteInput` の 400 だけを返し、通れば `repo.create`。`PUT /:id` も同じで、無ければ 404。
  - 入力の確認: `backend/src/routes/parse-route-input.ts` → `validation/fields.ts` の `text()`。ルート名は **前後の空白を取り除いた値** になる（1〜100文字）。
  - リポジトリ: `backend/src/routes/route-repository.ts`（`list`・`get`・`create`・`update`・`delete`）と `sqlite-route-repository.ts`。名前で探す口は無い。
  - 画面: `frontend/src/routes/RouteForm.tsx` は、失敗の応答に `fieldErrors` があれば `toRouteFormErrors`（`route-form.ts`）で欄ごとの文に分け、`field: "name"` の文を「ルート名」の欄の下に出す。**ステータスを見ていない** ので、409 でも本文が `ApiError`＋`fieldErrors` なら、今のコードのままで欄の下に出る（`api-client.ts` の `request` は 2xx 以外の JSON 本文をそのまま `error` に入れる）。
- API で 409 を返すところは、まだ1つも無い（初めて使うステータス）。
- 今の DB には、もう同じ名前のルートが2つある（Task の文から）。

## 2. 確かめること（選択肢・おすすめ・理由）

### Q1. 編集（`PUT /api/routes/:id`）でも、ほかのルートと同じ名前に変えるのを止めるか
| 選択肢 | 内容 |
|---|---|
| A | 登録（POST）だけ止める（Task の文のとおり） |
| **B（おすすめ）** | 編集でも、**名前を今と違う名前に変えるとき** に、ほかのルートと同じなら 409 |
| C | 編集でも、自分以外に同じ名前があれば常に 409 |

- 理由: A だと「別の名前で登録 → 編集で同じ名前に変える」で、また同じ状況が作れて、困りごとが直らない。C だと、今ある重複した2つのルートのどちらも、名前を変えずに運賃だけ直すことができなくなる（Q3）。B なら穴をふさぎつつ、今ある重複のルートも名前以外は今までどおり編集でき、別の名前に変えて重複を解消できる。
- Task の受け入れ条件「編集の動きは変わらない」は、「重複にならない編集は今までどおり」と読む。**ここは Task の文より広げるので、オーナーに必ず確かめる。**

### Q2. 「同じ名前」をどう比べるか
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 前後の空白を取り除いた後（今の `text()` の結果）で、文字が完全に同じなら同じ |
| B | A に加えて、英字の大文字・小文字を区別しない |
| C | Unicode の正規化（NFKC。全角・半角や「↔」と「<->」の違いなどを寄せる）をしてから比べる |

- 理由: 名前は日本語が中心で、B の効果は小さい。C は「違う名前のつもり」の2つを同じと判定して登録できない、という分かりにくさが出る。保存する値（前後の空白を除いたもの）と比べる値を同じにしておけば、説明も簡単。中の空白（「自宅 ↔本社」と「自宅↔本社」）は違う名前として扱う。

### Q3. すでに DB にある同じ名前のルートをどうするか
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | そのまま残す。オーナーが画面で片方の名前を変えるか消す |
| B | マイグレーションで、2つ目以降の名前を自動で変える（例: 「自宅↔本社 (2)」） |
| C | マイグレーションで、2つ目以降を消す |

- 理由: 今の重複は1組で、どちらを残すか・どう名付けるかはオーナーにしか決められない。B・C はデータを書き換えるので戻しにくい。C は記録のスナップショットには影響しないが、追加の移動の `sourceRouteId` などの手がかりが消える。A なら DB に手を入れない。

### Q4. 重複の確認をどこで行うか（DB の UNIQUE 制約を張るか）
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | API（入力の境界）で確かめるだけ。DB のスキーマは変えない |
| B | 新しいマイグレーションで `UNIQUE (user_id, name)` のインデックスを足し、制約違反を 409 にする |
| C | A と B の両方 |

- 理由: B・C は今ある重複（Q3）があると、インデックスを作るマイグレーションが失敗して backend が起動しなくなる。先にデータを直すマイグレーション（Q3 の B・C）が要り、戻しにくい変更が2つ重なる。利用者は1人で、`node:sqlite` の `DatabaseSync` は同期で動き、Express の1つのハンドラの中で「確かめる → 入れる」を await を挟まずに行えば、間に別のリクエストが割り込まない。CLAUDE.md の「バリデーションは API の受け口で行う」にも合う。将来、複数ユーザー・並行の書き込みを入れるときに B を考え直す（その時は ADR を書く）。
- 補足: A なら **DB のスキーマの変更は無い**。

### Q5. 409 の本文の `error`（上の段の文）を何にするか
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | `error: "同じ名前のルートがあります"`、`fieldErrors: [{ field: "name", message: "同じ名前のルートがあります" }]` |
| B | `error: "入力に誤りがあります"`（400 と同じ）、`fieldErrors` は A と同じ |

- 理由: 画面は `fieldErrors` があるとき上の段の `error` を出さないので、画面の見え方は A・B で同じ。`curl` や開発者ツールで見たとき、A のほうが 400 と区別しやすく、`docs/troubleshooting.md` で引きやすい。

### Q6. 入力の誤り（400）と重複（409）が同時にあるとき
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 先に今の入力の確認をし、400 ならそれを返す。入力が正しいときだけ重複を確かめる |
| B | 重複も入力の確認と一緒に集めて 400 で返す |

- 理由: Task が「重複は 409」と決めている。B だと重複が 400 になったり 409 になったりする。A ならステータスの意味が1つに決まる（直してから送り直すと、次に重複が分かる）。

### Q7. 画面で、送る前に一覧と比べて知らせるか
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | しない。API の 409 の文を欄の下に出すだけ（Task のとおり） |
| B | 入力中に、読み込み済みの一覧と比べて欄の下に知らせる |

- 理由: 判定を API の1か所にまとめる方針（`route-form.ts` の `toRouteInput` のコメント）に合う。B は判定（Q2）を2か所に持つことになり、ずれやすい。

### Q8. 要件定義の更新を、どの PR でするか
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 実装と同じ PR で `docs/requirements.md` も直し、PR は自動マージせずオーナーの確認を待つ（「確認が必要な項目」に書く） |
| B | 要件定義だけ先に別の PR にしてオーナーが確認し、マージ後に実装の PR |

- 理由: 変更は小さく、要件と実装を1つの PR で見比べられるほうが確認しやすい。1つの作業 = 1 PR の決まりにも合う。ただし要件定義の変更を含むので、**この PR は自動マージしない**。

### Q9. ADR を書くか
| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 書かない。要件定義の「決定の記録」に U11 として残す |
| B | ADR-0004「ルート名の重複は API で確かめ、DB の制約は張らない」を書く |

- 理由: Q4 の A は DB に何も残さないので、後から UNIQUE 制約を足すことも、確認をやめることもできる（後から変えにくいことではない）。ただし DEV_RULES は「迷わずに決めたことでも、後から変えにくいことなら書く」としており、「409 を初めて使う」ことを API の形の決定と見るなら B。**オーナーが B を選んだら、ADR を足し、PR の確認項目にも入れる。**

## 3. 要件（おすすめを採用したもの）

### やること

1. **リポジトリ**（`backend/src/routes/route-repository.ts`・`sqlite-route-repository.ts`）
   - 名前で探す口を1つ足す。例: `findByName(userId: string, name: string): Route[]`（同じ名前が今は複数ありうるので配列。または `existsName(userId, name, exceptId?)` のような真偽値でもよい）。
   - SQL は `WHERE user_id = ? AND name = ?`（完全一致・大文字小文字も区別。SQLite の `=` は既定で BINARY 比較なのでそのまま）。
   - テスト用の別実装があれば、それにも足す（`RouteRepository` を実装しているものすべて）。
2. **API**（`backend/src/routes/route-router.ts`）
   - `POST /`: `parseRouteInput` が通った後、同じ `userId` に同じ名前のルートがあれば、登録せずに **409**。本文は
     ```json
     { "error": "同じ名前のルートがあります", "fieldErrors": [{ "field": "name", "message": "同じ名前のルートがあります" }] }
     ```
   - `PUT /:id`: `parseRouteInput` が通った後、
     1. 対象のルートが無ければ、今までどおり 404。
     2. 送られた名前が対象のルートの今の名前と **違い**、かつ同じ名前のルートが（対象以外に）あれば、更新せずに上と同じ本文で **409**。
     3. 名前が今と同じなら、ほかに同じ名前があっても更新できる（今ある重複のため）。
   - 文は1か所の定数にして、POST と PUT で使い回す（`notFound` と同じ置き方）。
   - 「確かめる → 入れる/変える」の間に `await` を挟まない（同期のまま。§2 Q4）。
3. **画面**（`frontend/src/routes/`）
   - 409 の `fieldErrors` の `name` の文が「ルート名」の欄の下に、ほかの入力の誤りと同じ出し方（`field-error`・`aria-invalid`・`aria-describedby`）で出ること。今の `RouteForm.tsx` / `toRouteFormErrors` のままで出るはずなので、**コードは変えずにテストで確かめる**。出なければ直す。
   - 409 のとき、入力した値は消さない（今の失敗のときと同じ）。
   - 編集のフォームでも同じ出し方になる（Q1）。
4. **文書**（同じ PR）
   - `docs/requirements.md`:
     - F1 に「ルート名は、ほかのルートと同じにできない（前後の空白を除いて完全に同じなら同じ。登録と、名前を変える編集で確かめる）。すでにある同じ名前のルートは残し、名前を変えずに編集できる」を足す。
     - 「バリデーション」に「ルート名が、ほかのルートと同じでないこと（同じなら 409）」を足す。
     - 「決定の記録」に U11（今日の日付）として、Q1〜Q4 の決定を1行で足す。
   - `docs/api/openapi.yaml`: `POST /api/routes` と `PUT /api/routes/{id}` の responses に `"409"` を足す。`components/responses` に `Conflict`（example は上の本文）を足して参照する。`openapi.test.ts` は「メソッド＋パス」の数（15）を見ているだけなので、数は変わらない。
   - `docs/troubleshooting.md`（CLAUDE.md の決まり: メッセージ・ステータスを変えたら同じ PR で直す）:
     - 画面のメッセージの表に「同じ名前のルートがあります（欄の下に赤い文）」: 原因「ほかのルートと同じ名前で登録・名前の変更をしようとした（409）」、対処「別の名前にする。前からある同じ名前のルートは、片方の名前を変えるか消す」、見る場所 `backend/src/routes/route-router.ts`。
     - 「API のステータス」の表に 409 の行を足す。
   - `docs/PROGRESS.md` はセッションを終える前に更新する（いつもどおり）。
5. **テスト**（Vitest）
   - `sqlite-route-repository.test.ts`: 名前で探す口が、同じ名前・違う名前・ほかの `userId` を正しく分けること。
   - `route-router.test.ts`:
     - 同じ名前で POST → 409、本文が上の形、その後の GET の件数が増えていない。
     - 前後に空白を付けた同じ名前（`" 自宅↔本社 "`）でも 409。
     - 違う名前なら 201（今までどおり）。大文字小文字だけ違う英字の名前は 201（Q2）。
     - 名前が空など 400 の入力は、重複があっても 400（Q6）。
     - PUT: ほかのルートの名前に変える → 409 で、対象のルートは変わっていない。名前を変えずに運賃だけ変える → 200。
     - PUT: 同じ名前のルートが2つある状態（リポジトリに直接入れて作る）で、片方を名前そのまま編集 → 200。別の名前に変える → 200。
   - `route-form.test.ts`（または `routes-api.test.ts`）: 409 の本文を `toRouteFormErrors` に通すと `byField.name` に文が入り、`other` は空。

### やらないこと

- DB のスキーマの変更（UNIQUE 制約・インデックス・マイグレーション）。
- 今ある同じ名前のルートの自動の改名・削除（オーナーが画面で直す）。
- 全角・半角・大文字小文字・中の空白をそろえて比べること。
- 画面で送る前に一覧と比べて知らせること。
- 日次記録・追加の移動に残っているルート名（スナップショット）との比較。削除したルートと同じ名前は登録できる。
- 出勤のルートの選び方の表示の変更（出発地・運賃を併記するなど）。必要なら別の Task。
- ADR（Q9 で B と答えが来たら書く）。

### 受け入れ条件

- [ ] すでにある名前でルートを登録（POST）すると 409 で、本文は `{ error: "同じ名前のルートがあります", fieldErrors: [{ field: "name", message: "同じ名前のルートがあります" }] }`。ルートの件数は増えない
- [ ] 前後の空白だけが違う名前でも 409
- [ ] 違う名前なら、今までどおり 201 で登録できる
- [ ] 入力の誤りがあるときは、重複があっても今までどおり 400
- [ ] 画面の登録のフォームで重複すると、「同じ名前のルートがあります」がルート名の欄の下に、ほかの入力の誤りと同じ見た目で出る。入力した値は残る
- [ ] 編集で、ほかのルートと同じ名前に変えると 409 で、ルートは変わらない。画面では欄の下に同じ文が出る
- [ ] 編集で名前を変えなければ、今ある同じ名前のルートも今までどおり保存できる
- [ ] ルートの一覧・削除・出勤の保存・一括設定・追加の移動・CSV 出力の動きは変わらない（既存のテストがすべて通る）
- [ ] DB のスキーマ（`migrations.ts`）は変わっていない
- [ ] `docs/requirements.md`・`docs/api/openapi.yaml`・`docs/troubleshooting.md` が同じ PR で直っている
- [ ] `npm run typecheck && npm run lint && npm run test` が通る

## 4. 戻しにくい変更・PR の扱い

- **DB のスキーマの変更: 無し**（Q4 の A）。オーナーが Q4 で B・C を選んだ場合は、スキーマの変更と、今ある重複のデータを直すマイグレーション（Q3 の B・C）が要る。どちらも戻しにくいので、ADR を書き、別の PR で確認を受けてから実装する。
- **要件定義の変更: 有り**（F1・バリデーション・決定の記録 U11）。そのため実装の PR は **自動マージしない**。PR の本文の「確認が必要な項目」に「`docs/requirements.md` の変更（U11）」「Q1: 編集でも 409 にした（Task の文より広い）」を書く。
- API に 409 を足すのは、応答の種類が増えるだけで、今の呼び出し側（画面）は変えずに受けられる。後から外すのも簡単。
