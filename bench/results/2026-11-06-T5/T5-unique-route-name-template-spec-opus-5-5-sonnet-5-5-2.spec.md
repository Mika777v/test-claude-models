## 0. 今のコードで分かったこと（前提）

| 項目 | 今の動き | 場所 |
|---|---|---|
| ルート名の検証 | 必須・前後の空白を取る・100文字以内。**重複は見ていない** | `backend/src/validation/fields.ts` の `text()`、`backend/src/routes/parse-route-input.ts` |
| 登録・編集の API | 検証に失敗すると 400（`error: "入力に誤りがあります"` と `fieldErrors`）。成功は 201 / 200 | `backend/src/routes/route-router.ts` |
| DB | `routes` テーブルに `name` の UNIQUE 制約は無い。持ち主は `user_id` 列（今は固定値1つ） | `backend/src/db/migrations.ts`（version 1） |
| リポジトリ | `list / get / create / update / delete` だけ。名前で探すメソッドは無い | `backend/src/routes/route-repository.ts`・`sqlite-route-repository.ts` |
| 削除 | 行を本当に消す（論理削除ではない） | 同上 |
| 画面のエラーの出し方 | `fieldErrors` のうち `field` がフォームの欄名（`name` など）のものは欄の下に赤い文で出す。欄に結び付かないものはフォームの上に出す。ステータスコードは見ていない | `frontend/src/routes/route-form.ts` の `toRouteFormErrors`、`RouteForm.tsx` |
| 409 | まだどの API も使っていない（初めての 409） | `docs/api/openapi.yaml`・`docs/troubleshooting.md` に記載なし |
| 日次記録 | 出勤の記録はルートの値（名前を含む）をコピーして持つ。ルートの名前の重複とは関係しない | 要件定義 §5 |

**分かったこと**: `field: "name"` の `fieldErrors` を返せば、画面は **今のコードのまま** ルート名の欄の下に文を出す。画面の作業は「その動きをテストで確かめる」が中心になる。

## 1. オーナーに確かめること

### Q1. 編集（`PUT /api/routes/:id`）でも重複を止めるか 【重要】

Task には登録（POST）だけが書かれていて、受け入れ条件は「編集の動きは変わらない」。しかし、編集で別のルートと同じ名前に変えられると、また「自宅↔本社」が2つになる。

| 選択肢 | 内容 |
|---|---|
| A | 登録だけ止める（Task の文のとおり） |
| **B（おすすめ）** | 編集でも、**名前を変えたとき** に、ほかのルートと同じ名前なら 409 にする |
| C | 編集では、名前を変えたかどうかに関わらず、ほかのルートと同じ名前なら 409 にする |

**おすすめ: B。** 理由: 困っていること（出勤を選ぶときにどちらか分からない）は、編集でも同じように起きる。同じ判定を使うので作業は小さい。C だと、今すでに2つある「自宅↔本社」の片方の運賃だけを直したいときにも 409 になり、今の編集の動きが変わってしまう（Q2）。B なら、名前を変えない編集は今までどおり通る。

> B を採ると、Task の受け入れ条件「編集の動きは変わらない」は「名前を **別のルートと同じ名前に変える** 編集だけが 409 になる。それ以外の編集は変わらない」に読み替える。オーナーに確かめるときに、この点をはっきり伝える。

### Q2. すでに DB にある重複（今の「自宅↔本社」×2）をどうするか

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | そのまま残す。自動では直さない。一覧・出勤の選択・編集・削除は今までどおり使える。片方の名前を手で変えれば解消する |
| B | マイグレーションで、重複した名前に「(2)」などを自動で付ける |
| C | マイグレーションで DB に UNIQUE 制約を足す（重複が残っていると失敗するので、B とセット） |

**おすすめ: A。** 理由: 利用者は1人で、重複は手で1回名前を変えれば直る。B・C は保存しているデータを書き換える **戻しにくい変更**（DB のスキーマ・データの移し方）で、ADR とオーナーの確認が要る。今回の困りごとに対して大きすぎる。

### Q3. 重複の判定を DB の制約でするか、アプリ（API）でするか

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | API の受け口で、同じユーザーのルートに同じ名前があるかを調べる。DB は変えない |
| B | DB に `UNIQUE (user_id, name)` を足し、制約違反を 409 に変える |

**おすすめ: A。** 理由: Q2 で既存の重複を残すので、B の制約は今のデータでは作れない。B は DB のスキーマの変更（自動マージ不可・ADR が要る）になる。利用者は1人で、同時に2つ登録して両方通る心配は実際には無い。CLAUDE.md の「バリデーションは入力の境界（API の受け口）で行う」にも合う。
将来、複数ユーザーや同時の書き込みで DB の制約が要るようになったら、そのときに「重複の整理＋UNIQUE」のマイグレーションと ADR を書く（このとき戻しにくい変更になる）。

### Q4. 「同じ名前」とは何か（比べ方）

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 前後の空白を取った後の文字列が **完全に同じ** なら同じ（今の検証がすでに前後の空白を取っている） |
| B | A に加えて、全角/半角・大文字/小文字をそろえて（Unicode NFKC など）比べる。例: 「自宅↔本社」と「自宅 ↔ 本社」「ＡＢＣ」と「abc」 |

**おすすめ: A。** 理由: 動きが分かりやすく、テストも書きやすい。B は「なぜ違う名前なのに断られたのか」が利用者に分かりにくく、どこまでそろえるかの決め事が増える。見分けにくい名前が問題になったら、別の Task で足せる（後から変えやすい）。

### Q5. ほかの入力の誤り（400）と名前の重複（409）が同時にあるとき

例: 名前が重複していて、運賃も空。

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 先に今の検証をする。誤りがあれば 400 を返し、重複は調べない。検証が通ったときだけ重複を調べ、重複なら 409 |
| B | 重複も入力の誤りとして 400 に混ぜ、まとめて返す |

**おすすめ: A。** 理由: Task が 409 と決めている。400 と 409 を分けると、ステータスの意味が1つずつになる。欠点は、運賃を直して送り直した後に、初めて名前の重複が出ること。1人で使う登録の画面では大きな不便ではない。

### Q6. 409 の本文の `error`（全体の文）に何を入れるか

Task は「`field` は `"name"`、文は『同じ名前のルートがあります』」とだけ書いていて、`error` の文は決めていない。

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | `error` も `"同じ名前のルートがあります"` |
| B | `error` は 400 と同じ `"入力に誤りがあります"` |

**おすすめ: A。** 理由: 409 は 400 と別の理由なので、`curl` や開発者ツールで本文を見たときに理由がすぐ分かる。画面は `fieldErrors` があるときは `error` を出さないので、画面の見た目はどちらでも同じ。

### Q7. 画面で、送る前に一覧と比べて止めるか

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | しない。API の 409 の `fieldErrors` を、今の入力の誤りと同じく欄の下に出すだけ |
| B | 画面が持っているルートの一覧と比べ、送る前に欄の下に出す |

**おすすめ: A。** 理由: Task の「今の入力の誤りと同じ出し方」に合う。今の画面は、正しいかどうかの判定をすべて API に任せている（`route-form.ts` の `toRouteInput` のコメント）。判定を2か所に置くと、ずれる元になる。

### Q8. 要件定義（`docs/requirements.md`）を直すか、PR をどう分けるか

DEV_RULES では、要件定義の変更は自動マージせずオーナーに確認する。

| 選択肢 | 内容 |
|---|---|
| **A（おすすめ）** | 実装と同じ PR で、F1 に「ルート名は、ほかのルートと同じにできない」を1行足す。PR は自動マージを予約せず、本文の「確認が必要な項目」に書く |
| B | 要件定義は別の PR（`needs-confirm`）にし、実装の PR は自動マージする |
| C | 要件定義は直さない |

**おすすめ: A。** 理由: 決めたことのうち要件は `docs/requirements.md` に書く決まり（DEV_RULES「セッションとコンテキストの使い方」）。Q1 の答えで受け入れ条件が Task の文から少し変わるので、どのみちオーナーが見る。1 PR にまとめるほうが、要件と実装がずれない。

### Q9. ADR は要るか

**おすすめ: 要らない。** 理由: DB のスキーマもデータも変えず、API の判定を1つ足すだけで、後から変えやすい。「DB の制約にしなかった」ことは、PR 本文の「自分で決めたこと」と、この SPEC の Q3 に残す。Q2・Q3 で B / C を選ぶ場合は、DB のスキーマとデータを変える戻しにくい変更になるので、**ADR とオーナーの確認が要る**。

## 2. やること（おすすめを採用した場合の要件）

### 2.1 API（backend）

1. **`POST /api/routes`**
   - 今の検証（`parseRouteInput`）が失敗したら、今までどおり 400。
   - 検証が通ったら、同じユーザーのルートに、前後の空白を取った名前と完全に同じ名前があるかを調べる。
   - あれば、登録せずに **409** と次の本文を返す:
     ```json
     {
       "error": "同じ名前のルートがあります",
       "fieldErrors": [{ "field": "name", "message": "同じ名前のルートがあります" }]
     }
     ```
   - 無ければ、今までどおり登録して 201。
2. **`PUT /api/routes/:id`**
   - 今の検証が失敗したら 400（今までどおり）。
   - 対象のルートが無ければ 404（今までどおり）。
   - 名前が **今の名前から変わる** ときだけ、**自分以外の** 同じユーザーのルートに同じ名前があるかを調べ、あれば更新せずに 409（本文は POST と同じ）。
   - 名前が変わらない編集（運賃・区間・URL だけの変更）は、ほかに同じ名前のルートがあっても今までどおり 200。
   - 404 と 409 の順: 対象が無ければ 404 を先に返す。
3. 判定の置き場所（実装の目安。形は実装する人が決めてよい）
   - `RouteRepository` に、名前でルートを探すメソッドを足す（例: `findByName(userId, name): Route | undefined`。SQL は `WHERE user_id = ? AND name = ?`）。`SqliteRouteRepository` に実装する。
   - 「重複かどうか」の判断（POST は同じ名前があれば重複、PUT は名前が変わり、かつ自分以外に同じ名前があれば重複）は、テストしやすいよう純粋関数に分けてもよい。
   - 409 の本文の文は1か所に定数で置く（`notFound` と同じ書き方）。
4. 名前の比較は SQL の `=`（SQLite の既定の BINARY 照合。完全一致）で行う。`name` は検証で前後の空白を取った値なので、そのまま比べればよい。

### 2.2 画面（frontend）

- 登録・編集のフォームで 409 が返ったら、「同じ名前のルートがあります」を **ルート名の欄の下** に赤い文で出し、欄に `aria-invalid` を付ける（今の入力の誤りと同じ）。
- 今の `toRouteFormErrors` と `RouteForm` がこの動きをすでにするので、**コードの変更は要らない見込み**。要るのはテスト（2.4）。もし動かなければ、そのときに直す。
- 409 のとき、フォームに入れた値は消さない（今の 400 と同じ。成功したときだけ空にしている）。
- 送る前に一覧と比べることはしない（Q7）。

### 2.3 文書（同じ PR で直す）

| ファイル | 直すこと |
|---|---|
| `docs/api/openapi.yaml` | `POST /api/routes` と `PUT /api/routes/{id}` に `"409"` を足す。`components/responses` に `Conflict`（例: 上の本文）を足して参照する。（`openapi.test.ts` はメソッドとパスだけを照合するので、テストは変わらない） |
| `docs/troubleshooting.md` | 「画面に出るメッセージ」に「同じ名前のルートがあります」の行（原因: 同じ名前のルートがすでにある。409。対処: 別の名前にするか、今あるルートを編集する。場所: `backend/src/routes/route-router.ts`）。「API のステータス」の表に 409 の行。DEV_RULES の決まり（画面のメッセージ・API のステータスを足したら同じ PR で直す） |
| `docs/requirements.md` | F1 に「ルート名は、ほかの自分のルートと同じにできない（前後の空白を除いて完全に同じなら同じ名前）。すでに同じ名前が複数あるときは、名前を変えるまでそのまま使える」を足し、更新日を直す（Q8）。**要件定義の変更なので、オーナーの確認が要る** |

### 2.4 テスト

- backend `route-router.test.ts`
  - 登録済みと同じ名前で POST → 409・本文が上の形・一覧の件数が増えない
  - 前後に空白を付けた同じ名前（`"  自宅↔本社 "`）で POST → 409
  - 違う名前で POST → 201
  - 名前が重複し、ほかの欄も誤り → 400（409 ではない）
  - PUT で別のルートと同じ名前に変える → 409・そのルートは変わらない
  - PUT で名前を変えずに運賃だけ変える → 200
  - DB に同じ名前が2つある状態（リポジトリに直接2件入れる）で、片方の運賃だけを PUT → 200
  - 同じ名前のルートを削除した後なら、その名前で POST → 201
  - 存在しない id に、重複する名前で PUT → 404
- backend `sqlite-route-repository.test.ts`: 名前で探すメソッド（見つかる・見つからない・ほかのユーザーのルートは見つからない）
- frontend `route-form.test.ts`: `field: "name"` の重複の `fieldErrors` が `byField.name` に入り、`other` が空になる

## 3. やらないこと

- DB のスキーマの変更（UNIQUE 制約・マイグレーション）
- すでに DB にある重複の自動の整理・名前の付け替え
- 全角/半角・大文字/小文字・途中の空白をそろえた比較
- 画面での送る前の重複チェック
- 出発地・到着地・運賃など、名前以外の項目の重複の判定
- 日次記録・追加の移動（記録にコピーしたルート名）への影響。記録は変えない
- ADR の追加（Q2・Q3 で別の答えになった場合を除く）

## 4. 受け入れ条件

- [ ] すでにある名前でルートを登録しようとすると 409 で、本文は `{ error: "同じ名前のルートがあります", fieldErrors: [{ field: "name", message: "同じ名前のルートがあります" }] }`。ルートは増えない
- [ ] 前後の空白だけが違う名前も、同じ名前として 409 になる
- [ ] 違う名前なら、今までどおり 201 で登録できる
- [ ] ほかの欄に入力の誤りがあるときは、今までどおり 400（名前が重複していても）
- [ ] 編集で、名前を別のルートと同じ名前に変えると 409 で、ルートは変わらない（Q1 で B を採った場合）
- [ ] 名前を変えない編集は、ほかに同じ名前のルートがあっても今までどおり保存できる
- [ ] 消したルートと同じ名前は、また登録できる
- [ ] 画面の登録のフォームで、「同じ名前のルートがあります」がルート名の欄の下に、今の入力の誤りと同じ見た目で出る。入れた値は消えない
- [ ] ルートの一覧・削除・出勤の保存・一括設定・追加の移動・月の表示など、ほかの動きは変わらない（今のテストがすべて通る）
- [ ] `docs/api/openapi.yaml`・`docs/troubleshooting.md`・`docs/requirements.md` が同じ PR で直っている
- [ ] `npm run typecheck && npm run lint && npm run test` が通る

## 5. 戻しにくい変更があるか

- **おすすめどおりなら、戻しにくい変更は無い。** DB のスキーマ・保存したデータは変えない。API の判定を1つ足すだけで、外せば元に戻る。
- ただし **要件定義（`docs/requirements.md`）の変更を含む** ので、PR は自動マージを予約せず、本文の「確認が必要な項目」に書いてオーナーに確認する（Q8）。
- Q2・Q3 で B / C（既存の重複の書き換え・UNIQUE 制約）を選ぶ場合は、**DB のスキーマの変更とデータの書き換え** になり戻しにくい。そのときは ADR を書き、マイグレーションを別の PR にして、オーナーの確認を取る。

## 6. PR のメモ（実装する人へ）

- タイトルの例: `feat(backend): 同じ名前のルートを登録できないようにする`（scope は `.github/workflows/pr-title.yml` にある frontend・backend・shared・db・docs・textbook・ci・deps だけ。`routes` は使えない。scope は省いてもよいので、`feat: …` でもよい）
- 本文に `Closes #<この Task の番号>`。「確認が必要な項目」に「要件定義の変更（F1 に1行）」と「Q1: 編集でも名前の変更時は 409 にした」を書く
- 「自分で決めたこと」に Q3（DB の制約にせず API で判定）・Q4（完全一致）・Q5（400 を先に）を書く
