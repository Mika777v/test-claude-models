## 1. 確かめること（選択肢・おすすめ・理由）

### Q1. 「片付ける」とは何か（いちばん大事）

| 案 | 内容 |
|---|---|
| A | **「使わない」にしまう（アーカイブ）。** 一覧の下の方にまとめ、出勤などの選択肢から消す。いつでも「使う」に戻せる。削除も今のまま残す |
| B | 今の削除で足りる（作るものは無い。削除の存在を伝える・確認の文を直す程度） |
| C | 使う期間（使い始め・使い終わりの日）をルートに持たせ、その日付の範囲外では選択肢に出さない |
| D | 一覧の並べ替え（よく使う順・手で並べる）で目立たなくする |

- **おすすめ: A**
- 理由:
  - 転勤は戻ることがある。運賃・経路の URL（`searchUrl`）を入れ直さずに戻せる
  - 削除は戻せないので「念のため残す」ルートが増え、それがごちゃごちゃの原因になる。戻せる片付け方があれば迷わず押せる
  - 過去の記録はもともとコピーで持つので、しまっても削除しても記録は変わらない。A は記録の形に手を入れない
  - C は「転勤の日」を入れる手間と、一括設定の期間との組み合わせ（期間の途中で使えなくなる）で作りが重い。今の悩み（選択肢が多い）には A で足りる
  - D は数が減らないので、選択肢のごちゃごちゃは解けない

### Q2. 削除は残すか

| 案 | 内容 |
|---|---|
| A | 残す。使っているルートにも、しまったルートにも「削除」を出す（今と同じ） |
| B | しまったルートにだけ「削除」を出す（2段階にする） |
| C | 削除をやめ、しまうだけにする |

- **おすすめ: A**
- 理由: 打ち間違いで作ったルートは、しまわずにすぐ消したい。B は手数が増え、C は API を消すことになり（戻しにくい）、要件 F1 の「削除ができる」も変わる。今の削除は記録を壊さないので、残しても困らない

### Q3. しまった状態の持ち方（DB・型）

| 案 | 内容 |
|---|---|
| A | `routes` に `archived_at TEXT`（NULL = 使っている、日時 = しまった日時）を足す。型は `Route` に任意の `archivedAt?: string` |
| B | `archived INTEGER NOT NULL DEFAULT 0`（0/1）。型は `archived: boolean` |
| C | `status TEXT`（`'active' \| 'archived'`）。型は判別可能なユニオン |

- **おすすめ: A**
- 理由:
  - `ALTER TABLE ... ADD COLUMN` だけで済み、今までの行は NULL（= 使っている）のまま読める（v3 の `search_url` と同じやり方）
  - いつしまったかが残るので、「しまったルート」を新しくしまった順に並べられる
  - 「無ければ項目を出さない」は `searchUrl` と同じ決まり（DB の NULL は JSON に出さない）。今のコードと揃う
  - C は状態が2つしか無いうちは大げさ。状態が増えたら、そのとき新しい番号のマイグレーションで替える
- **戻しにくい変更: DB のスキーマを変える（マイグレーション v4）。** オーナー確認の PR にし、ADR を書く（§4）

### Q4. しまう・戻す の API の形

| 案 | 内容 |
|---|---|
| A | 専用の API: `PUT /api/routes/:id/archive`（しまう）・`DELETE /api/routes/:id/archive`（戻す）。どちらも本文なし、更新後の `Route` を返す |
| B | 今の `PUT /api/routes/:id` の本文に `archived` を足す |
| C | `PATCH /api/routes/:id` を足し、`{ archived: boolean }` を送る |

- **おすすめ: A**
- 理由:
  - 今の `PUT` は「全部の項目を送って置き換える」形で、編集フォームから呼ぶ。B にすると、編集のたびにしまった状態も送る必要があり、送り忘れで勝手に戻る事故が起きる
  - 「しまう」は何度呼んでも同じ結果（冪等）になり、PUT/DELETE の意味に合う。C はこのプロジェクトに PATCH が無く、部分更新の検証を新しく作ることになる
  - `RouteInput` は `Omit<Route, "id" | "userId">` なので、`Route` に `archivedAt` を足すと `RouteInput` にも入ってしまう。**`RouteInput` からは `archivedAt` も外す**（編集・登録では送らせない）

### Q5. 一覧の API は、しまったルートも返すか

| 案 | 内容 |
|---|---|
| A | `GET /api/routes` は今までどおり全件を返す（`archivedAt` 付き）。画面が分ける |
| B | 既定は使っているものだけ。`?include=archived` で全件 |
| C | `GET /api/routes/archived` を別に作る |

- **おすすめ: A**
- 理由: 利用者は1人で件数も少ない。ルートの画面は両方を出すので、1回の読み込みで済む。分け方（使っているルートだけ）は `shared/` の純粋関数1つ（例: `activeRoutes`）にして3つの画面から使い、テストを書く。B・C は API の形が増え、OpenAPI と画面の両方に手が要る

### Q6. 選択肢から外す場所

| 案 | 内容 |
|---|---|
| A | 3か所すべて: 日の編集パネルの出勤ボタン・一括設定のルート・追加の移動の「ルートから選ぶ」 |
| B | 出勤の2か所だけ（追加の移動では選べるまま） |

- **おすすめ: A**
- 理由: 依頼は「出勤を選ぶときの選択肢」だが、転勤で使わなくなったルートは客先としても使わない見込みが高い。場所ごとに出る・出ないが違うと分かりにくい。必要になったら戻せばよい（Q1 の A）

### Q7. しまったルートを、記録に新しく使えるか（API の受け口）

| 案 | 内容 |
|---|---|
| A | 使えない。出勤の保存（日の PUT・一括の下見・一括の登録）で、しまったルートの `routeId` は 400 にする |
| B | 使える（画面で隠すだけ）。API は今のまま |

- **おすすめ: A**
- 理由:
  - CLAUDE.md の「バリデーションは入力の境界（API の受け口）で行う」に合う。別のタブで開いたままの古い画面からでも、しまったルートで記録が作られない
  - 今の作りで、すでにその日の記録が同じルートのときは、日の編集パネルは保存を呼ばない（`isSameChoice` で止める）ので、しまったルートの日を開いても 400 にはならない
  - 一括の登録は当てはめた日だけを送り、当てはめの勤務区分は使っているルートからしか選べないので、ふつうの操作では当たらない
- エラーの文: `fieldErrors` の `workStyle.routeId` に「使わないにしたルートは選べません。ルートの画面で戻してください」。全体の `error` は今の「入力に誤りがあります」に合わせる
- 追加の移動の `sourceRouteId` は今も存在を確かめていない（値はコピー済みで、元のルートは目印だけ）。**ここは変えない**

### Q8. しまったルートを使っている日の見え方

| 案 | 内容 |
|---|---|
| A | 今のまま。カレンダー・表・CSV はコピーの名前で出し、印は付けない。日の編集パネルでは、今の選択としてそのルートのボタンが1つ出る（`buildOptions` の今の動き） |
| B | 「（使わない）」などの印を付ける |

- **おすすめ: A**
- 理由: U7（削除済みの印は付けない）と同じ考え方。過去の記録は「その日にそのルートで出勤した」事実で、今使うかどうかとは関係が無い。B にすると表・CSV の文字も変わり、F7 の列の決まりにも響く

### Q9. ルートの画面の見せ方

| 案 | 内容 |
|---|---|
| A | 一覧を「使っているルート」と「使わないルート（n件）」に分ける。後者は最初は閉じておき、押すと開く（`<details>`） |
| B | 「使わないルートも表示する」のチェックで切り替える |
| C | しまったルートは別の画面 |

- **おすすめ: A**
- 理由: 件数が見えるので、しまったルートがあることを忘れない。閉じておけば一覧はすっきりする。`<details>` なら新しい状態も依存も要らない。C は画面の流れ（§4 の図）が変わり大げさ

### Q10. しまったルートの編集

- **おすすめ: できる**（「編集」「使う に戻す」「削除」を出す）。運賃が変わったのを直してから戻すこともあるため。編集してもしまったままにする（`PUT` は `archived_at` に触らない）

### Q11. 一度に何件もしまう（複数選んで一括）

- **おすすめ: やらない。** 転勤で数件、という頻度なら1件ずつで足りる。必要になったら別の Task にする

### Q12. 確認のダイアログ

- **おすすめ: しまう・戻すは確認を出さない**（すぐ戻せるため）。結果は今の「「◯◯」を削除しました」と同じ帯に「「◯◯」を使わないにしました」「「◯◯」を使うに戻しました」と出す。削除の確認は今のまま

## 2. 要件（上のおすすめを採用した場合）

### やること

**データ・型（`shared/`）**
1. `Route` に任意の `archivedAt?: string`（しまった日時。ISO 8601）を足す。無ければ使っているルート
2. `RouteInput` を `Omit<Route, "id" | "userId" | "archivedAt">` にする（登録・編集では送らない）
3. 使っているルートだけを返す純粋関数（例: `activeRoutes(routes)`）と、しまったルートを新しくしまった順に返す関数（例: `archivedRoutes(routes)`）を `shared/` に置き、テストを書く

**DB（`backend/src/db/migrations.ts`）**
4. マイグレーション v4: `ALTER TABLE routes ADD COLUMN archived_at TEXT;`（v1〜v3 は書き換えない）。今までの行は NULL（使っている）のまま
5. `SqliteRouteRepository` の読み出しで、`archived_at` が NULL でなければ `archivedAt` を付ける（`searchUrl` と同じ）

**API（`backend/src/routes/`）**
6. `RouteRepository` に `archive(userId, id)`・`unarchive(userId, id)` を足す（見つからなければ undefined、あれば更新後の `Route`）
7. `PUT /api/routes/:id/archive`: しまう。すでにしまっていれば日時は変えずに 200。無ければ 404「ルートが見つかりません」
8. `DELETE /api/routes/:id/archive`: 戻す。すでに使っていれば 200。無ければ 404
9. `PUT /api/routes/:id`（編集）は `archived_at` を変えない。本文に `archivedAt` が来ても無視する（今の `parseRouteInput` は知らない項目を拾わないので、そのままでよい）
10. `GET /api/routes` は今までどおり全件（`archivedAt` 付き）
11. `resolveWorkStyle` の呼び出し元（日の PUT・一括の下見・一括の登録）で、しまったルートは 400。`fieldErrors` の `workStyle.routeId` に「使わないにしたルートは選べません。ルートの画面で戻してください」。見つからないときの今のエラーとは文を分ける
    - `resolveWorkStyle` が「見つからない」と「しまってある」を見分けて返せる形にする（例: 判別可能なユニオンの結果）
12. `docs/api/openapi.yaml` に2つの API と `archivedAt` を足す（`openapi.test.ts` の「メソッド＋パス」の一致のテストが通ること）

**画面（`frontend/`）**
13. `routes-api.ts` に `archiveRoute(id)`・`unarchiveRoute(id)` を足す（fetch を差し替えたテストを書く）
14. ルートの画面: 一覧を「使っているルート」と「使わないルート（n件）」（`<details>`、最初は閉じる。0件なら出さない）に分ける
    - 使っているルートの切符: 「経路を見る」「編集」「使わない」「削除」
    - 使わないルートの切符: 「経路を見る」「編集」「使うに戻す」「削除」。見た目で使っているルートと見分けられるようにする（例: 切符の色を薄く。色は `styles.css` の `:root` の決まりに合わせる）
    - しまう・戻すは確認なしで、結果を帯（`notice`）に出す。編集中のルートをしまっても、編集のフォームはそのまま
    - 使っているルートが0件で、使わないルートがあるとき: 「使っているルートがありません。左のフォームで登録するか、下の「使わないルート」から戻してください。」
15. 日の編集パネル・一括設定・追加の移動のフォームは、`activeRoutes` で絞ったルートだけを選択肢に出す
    - 日の編集パネルで、その日の記録のルートがしまってあるときは、今の `buildOptions` のとおり、コピーの名前で今の選択として1つ出す（選び直すと、それは消える）
    - 一括設定の最初のルートは、使っているルートの先頭
    - 使っているルートが0件のときの文: 日の編集パネル「使っているルートが無いので、出勤は選べません。「ルート」の画面で登録するか、戻してください。」・一括設定「使っているルートが無いので、出勤は選べません。」
16. 追加の移動を編集するとき、その `sourceRouteId` がしまったルートでも、入力済みの値はそのまま残る（選択欄は「手で入力する」の表示になってよい）

**文書（同じ PR か、続きの PR で）**
17. `docs/requirements.md`: F1 に「使わないにする・戻す」を足し、§5 の Route に `archivedAt`、決定の記録に新しい番号（例: U11）を足す。§4 の画面の流れの「ルート管理画面」の括弧に「使わない」を足す
18. `docs/adr/0004-...md`: 片付けを「しまう（`archived_at`）」で表すと決めた ADR（Q1・Q3・Q4 の選択肢と理由）。`docs/adr/README.md` の表にも足す
19. `docs/troubleshooting.md`: 新しいエラーの文（Q7）と、変えた画面の文（14・15）を足す・直す。例: 「出勤の選択肢にルートが出ない → 使わないにしてある（正常）→ ルートの画面の「使わないルート」から戻す」
20. `docs/PROGRESS.md` を作業の区切りで更新する

### やらないこと

- 一括でしまう・戻す（複数選択）
- ルートの使用期間（日付の範囲）での自動的な非表示（Q1 の C）
- ルートの並べ替え（手で並べる・よく使う順）
- 記録・表・CSV への「使わない」「削除済み」の印（Q8。U7 と同じ）
- 削除の仕組みの変更（物理削除のまま。確認の文も今のまま）
- しまったルートを持つ過去の記録の書き換え（記録はコピーなので触らない）
- 追加の移動の `sourceRouteId` の存在・状態の確認
- 一定期間使わないルートを自動でしまう

### 受け入れ条件

1. マイグレーション v4 を当てても、今までのルートはすべて「使っている」として一覧・選択肢に出る。今までの記録の表示・月の合計・CSV は変わらない
2. ルートの画面で「使わない」を押すと、そのルートは「使わないルート（n件）」に移り、日の編集パネル・一括設定・追加の移動の選択肢から消える（画面を読み直しても同じ）
3. 「使うに戻す」を押すと、元の「使っているルート」に戻り（並びは登録順のまま）、3つの選択肢にまた出る。名前・区間・運賃・経路の URL は変わらない
4. しまったルートを使った過去の日は、カレンダー・表・CSV で今までと同じ名前・金額で出る。印は付かない
5. しまったルートの日を日の編集パネルで開くと、今の選択としてそのルートが押された状態で出る。別の区分を選ぶと保存でき、その後はそのルートのボタンは出ない
6. API に直接、しまったルートの `routeId` で日の PUT・一括の下見・一括の登録を送ると 400 で、`fieldErrors` の `workStyle.routeId` に Q7 の文が入る。存在しない `routeId` は今までどおりの 400 の文
7. `PUT`/`DELETE /api/routes/:id/archive` は、何度呼んでも同じ結果で 200。無い id は 404。しまった日時は、2回目のしまうで変わらない
8. しまったルートを編集して保存しても、しまったまま。使っているルートを編集しても、しまわれない
9. しまったルートも、使っているルートも削除でき、削除した後の記録は今までどおり残る
10. 使っているルートが0件のとき、3か所で出勤が選べず、§2 の 14・15 の文が出る
11. `shared/` の絞り込みの純粋関数、repository（v4 の読み書き）、router（しまう・戻す・400 の場合）、`routes-api.ts` にテストがある。`npm run typecheck && npm run lint && npm run test` が通る
12. `docs/api/openapi.yaml`・`docs/troubleshooting.md`・`docs/requirements.md`・ADR が、作ったものと合っている

## 4. 進め方の案（1つの作業 = 1 PR）

Epic「使わなくなったルートを片付ける」を立て、次の Task に分ける。
