# SPEC: 使わなくなったルートを片付ける

- 作成日: 2026-11-06
- 元の依頼（Task）: 転勤で使わなくなったルートがいくつかあり、ルートの一覧と、出勤を選ぶときの選択肢がごちゃごちゃしてきた。使わなくなったルートを片付けられるようにしてほしい。
- 状態: **案**（下の「オーナーに確かめること」は、おすすめを採用したものとして要件を書いている。オーナーの回答で変わったら、要件も直す）

---

## 0. 調べてわかったこと（今の作り）

| 項目 | 今の作り | 場所 |
|---|---|---|
| ルートの削除 | **もうある**（F1）。画面の確認の後、`DELETE /api/routes/:id` で行を消す（物理削除。元に戻せない） | `frontend/src/routes/RoutesPage.tsx`・`backend/src/routes/route-router.ts`・`sqlite-route-repository.ts` |
| 削除したルートを使った記録 | 記録はルートの値のコピー（`RouteSnapshot`）を持つので、金額・区間・名前は残る。削除済みの印は出さない（U7） | `docs/requirements.md` §5・`backend/src/db/migrations.ts`（`daily_records` に外部キーなし） |
| 出勤の選択肢 | 日の編集パネル・一括設定・追加の移動の「ルートから選ぶ」は、`GET /api/routes` の全件を並べる | `DayPanel.tsx`（`buildOptions`）・`BulkDialog.tsx`・`bulk-form.ts`（`initialBulkForm` は先頭のルートを選んでおく）・`ExtraTripForm.tsx` |
| 記録のルートが一覧に無いとき | 日の編集パネルは、記録のコピーの名前で「今の選択」として出す | `DayPanel.tsx` の `buildOptions` |
| 出勤を保存するとき | backend が `routeId` のルートを引いて値をコピーする。**ルートが無ければ 400「選んだルートが見つかりません」** | `backend/src/daily-records/resolve-work-style.ts`・`daily-record-router.ts` |
| 一覧の並び | 作った順（`created_at, id`） | `sqlite-route-repository.ts` の `list` |

**つまり、「片付ける」手段としての削除はすでにある。** それでも依頼が来ているのは、削除だと次の点が困るからだと考えられる（オーナーに確かめる → Q1）。

- 削除すると元に戻せない（また同じ勤務先に戻る・登録の値を見返したい、ができない）
- 削除した後に、**過去の日を直して「その古いルートで出勤」にし直すことができない**（選択肢に出ず、出しても backend が 400 を返す）。転勤の前の月の入力漏れ・誤りを後から直すのは、ありそうな場面
- 経路の URL（`searchUrl`）など、記録にコピーしない値は削除で失われる

## 1. オーナーに確かめること（選択肢・おすすめ・理由）

### Q1. 「片付ける」は何をすることか
| 案 | 中身 |
|---|---|
| A | 今の削除で足りる（作るものは無し。削除の文言・場所を見直すだけ） |
| **B（おすすめ）** | **「使わない」にする（アーカイブ）を足す。** 一覧の下の方にまとめて畳み、出勤などの選択肢から外す。いつでも「使う」に戻せる。削除は今のまま残す |
| C | 削除をやめ、すべてアーカイブにする |

- おすすめ: **B**
- 理由: 依頼の困りごとは「並んでいてごちゃごちゃする」ことで、消したいこと自体ではない。B なら戻せるので、迷わず片付けられる。過去の日を古いルートで直すこともできる（Q4）。完全に消したいときのために削除は残す（C だと、試しに作ったルートなども消せなくなる）。

### Q2. どうやって「使わない」に分けるか
| 案 | 中身 |
|---|---|
| **A（おすすめ）** | **手で1件ずつ「使わない」にする**（ルートの一覧のボタン） |
| B | 最後に使った日から一定の期間（例: 3か月）たったら、自動で外す |
| C | ルートに「使う期間（いつまで）」を入れ、その日より後の日の選択肢から外す |

- おすすめ: **A**
- 理由: 個人利用でルートは数件。B は「一時的に使っていないだけ」のルートも外れてしまい、なぜ消えたかわかりにくい。C は日付ごとに選択肢が変わり、スキーマも判定も重くなる。A で困ったら後から B・C を足せる。

### Q3. 「使わない」ルートは、どの選択肢から外すか
| 案 | 中身 |
|---|---|
| **A（おすすめ）** | **新しく選ぶ場面のすべてから外す**: 日の編集パネルの出勤のボタン・一括設定のルート・追加の移動の「登録済みのルートから選ぶ」 |
| B | 出勤（日の編集パネル・一括設定）だけから外し、追加の移動では選べるままにする |

- おすすめ: **A**
- 理由: 転勤で使わなくなった区間は、臨時の移動でも使わないことが多い。使うなら「使う」に戻せばよい。場面ごとに違うとわかりにくい。

### Q4. すでに「使わない」ルートで記録している日は、どう見せ、どう扱うか
| 案 | 中身 |
|---|---|
| **A（おすすめ）** | **記録の表示は変えない**（コピーの値のまま。印も付けない）。その日の編集パネルでは、今の選択としてそのルートのボタンを出す（削除したときと同じ扱い）。backend は「使わない」ルートでの出勤の保存も受け付ける |
| B | backend で、「使わない」ルートでの新しい保存を 400 で断る |

- おすすめ: **A**
- 理由: 「使わない」は一覧を見やすくするための印で、データとして誤りではない。B だと、過去の日を直すために一度「使う」に戻す手間がかかり、別のタブで「使わない」にした直後の保存が失敗する。U7（削除済みの印を付けない）とも揃う。過去の日を古いルートで直したいときは、ルートを「使う」に戻して選べばよい。

### Q5. 「使わない」ルートの一覧での見せ方と、できる操作
| 案 | 中身 |
|---|---|
| **A（おすすめ）** | **一覧の下に「使わなくなったルート（N件）」として畳んで出す**（最初は閉じている）。操作は「使うに戻す」「削除」。編集は「使う」に戻してから |
| B | 一覧から完全に隠し、「使わないルートも表示」のチェックで出す |
| C | 一覧に並べたまま、灰色にするだけ |

- おすすめ: **A**
- 理由: C はごちゃごちゃが減らない。B は戻す手段が見つけにくい。A なら件数が見えて、開けばすぐ戻せる。編集を出さないのは、ボタンを減らすため（使わないルートを直す場面は少ない）。

### Q6. 削除は残すか・削除の条件を変えるか
| 案 | 中身 |
|---|---|
| **A（おすすめ）** | **今のまま残す**（使う・使わないのどちらからでも削除できる。確認の文言も今のまま） |
| B | 「使わない」にしたルートだけ削除できるようにする（2段階） |

- おすすめ: **A**
- 理由: 打ち間違えて作ったルートをすぐ消せなくなるのは不便。削除しても記録は変わらない（U7）ので、2段階にする必要は薄い。

### Q7. API の形
| 案 | 中身 |
|---|---|
| **A（おすすめ）** | **`POST /api/routes/:id/archive` と `POST /api/routes/:id/unarchive`** を足す。本文なし。返すのは更新後の `Route`。`GET /api/routes` は今までどおり全件を返し、各ルートに `archivedAt`（使わないにした日時。使うルートには項目なし）を付ける。画面で分ける |
| B | `RouteInput` に `archived` を足し、今の `PUT /api/routes/:id` で変える |
| C | `GET /api/routes?archived=false` のように、取得の段階で分ける |

- おすすめ: **A**
- 理由: B だと、編集のフォームが毎回 `archived` を送る必要があり、送り忘れで勝手に戻るおそれがある。C だと、記録のルートの名前を引くために全件も別に取ることになる。A は操作の意味が URL で読め、編集の入力（`RouteInput`）を変えずに済む。
- 同じ状態にもう一度しても成功（冪等）にする（例: 使わないルートに `archive` → 200、`archivedAt` は最初の日時のまま）。無い id は 404「ルートが見つかりません」。

### Q8. 並び順を変えるか（今回の範囲か）
| 案 | 中身 |
|---|---|
| **A（おすすめ）** | **今回は変えない**（作った順のまま） |
| B | 手で並べ替えられるようにする／よく使う順にする |

- おすすめ: **A**
- 理由: 依頼の困りごとは「使わないものが混ざる」ことで、アーカイブで解ける。並べ替えは別の Task にする（スキーマに並び順の列が要る）。

## 3. 要件（おすすめを採用した場合）

### やること

#### 共有の型（`shared/`）
- `Route` に任意の項目 `archivedAt?: string`（ISO 8601 の日時。使うルートには項目を付けない。`searchUrl` と同じく、DB の NULL は「項目が無い」にする）。
- `RouteInput`・`RouteSnapshot` は変えない（記録にはコピーしない）。
- 純粋関数 `activeRoutes(routes)` / `archivedRoutes(routes)`（名前は任意）で、使う・使わないに分ける。並びは元の順を保つ。テストを書く。

#### backend
- migration version 4: `ALTER TABLE routes ADD COLUMN archived_at TEXT;`
- `RouteRepository` に `archive(userId, id)` と `unarchive(userId, id)` を足す（見つからなければ `undefined`、あれば更新後の `Route`）。`archive` は、すでに使わないなら `archived_at` を変えない。
- `list`・`get` は `archivedAt` も返す。**`update`（PUT）は `archived_at` を変えず、返す `Route` にも `archivedAt` を含める**（今の `update` は入力から返す値を組み立てているので、そのままだと項目が落ちる）。
- `POST /api/routes/:id/archive`・`POST /api/routes/:id/unarchive`: 200 で更新後の `Route`。無い id は 404「ルートが見つかりません」（今のメッセージを使う）。
- `GET /api/routes` は全件（使わないものを含む）を返す。
- 出勤の保存（`resolveWorkStyle`）は変えない。使わないルートでも、存在すれば受け付ける（Q4）。
- `docs/api/openapi.yaml` に2つのパスと `archivedAt` を足す（`openapi.test.ts` の「メソッド＋パス」の一致が通ること）。

#### 画面: ルートの一覧（`RoutesPage.tsx`・`RouteTicket.tsx`）
- 使うルートの切符に「使わない」ボタンを足す（確認は出さない。すぐ戻せるため）。押したら「「◯◯」を使わないルートにしました」と出す。
- 使うルートの一覧の下に、使わないルートを「使わなくなったルート（N件）」として畳んで出す（`<details>` など。最初は閉じている。0件なら出さない）。
- 使わないルートには「使うに戻す」「削除」を出す（編集は出さない）。戻したら「「◯◯」を使うルートに戻しました」と出す。
- 編集中のルートを「使わない」にしたら、編集をやめる（削除と同じ）。
- 使うルートが0件で、使わないルートだけがあるときは、「使うルートがありません…」と出し、畳んだ一覧は出す。
- 見た目は今の切符のデザイン（`styles.css` の `:root`）に合わせ、使わないものは目立たない色にする。

#### 画面: 選択肢から外す（Q3）
- 日の編集パネルの出勤のボタン・一括設定のルートの選択・追加の移動の「登録済みのルートから選ぶ」には、**使うルートだけ**を並べる。
- 一括設定の最初に選んでおくルート（`initialBulkForm`）は、使うルートの先頭。使うルートが0件なら、今の「ルートが無いので、出勤は選べません。」と同じ扱い。
- 日の編集パネルで、記録（または当てはめ中の内容）のルートが使わないルートなら、今の選択としてそのボタンを出す（今の「一覧に無い」ときの扱いと同じ。名前は記録のコピー）。
  - `CalendarPage` は全件のルートを持ち続け、並べるときだけ使うルートに絞る（`toDraftWorkStyle` などが、使わないルートの id でも値を引けるように）。
- 追加の移動を編集するとき、元のルート（`sourceRouteId`）が使わないルートでも、入っている値はそのまま残る（今の、ルートを削除したときと同じ）。

#### 表示・CSV
- カレンダー・表・月の合計・CSV は変えない（記録のコピーを使っているため）。

#### 文書
- `docs/requirements.md`: F1 に「使わない（アーカイブ）にでき、出勤などの選択肢から外れる。いつでも戻せる。過去の記録の表示は変わらない」を足す。§5 の Route に `archivedAt`。決定の記録に U11（この SPEC の Q1〜Q8 の答え）。
- `docs/adr/0004-...md` と `docs/adr/README.md` の表。
- `docs/troubleshooting.md`: 画面の新しいメッセージ（「使わないルートにしました」など）と、「出勤の選択肢にルートが出ない → 使わないルートになっている。ルートの画面の『使わなくなったルート』から戻す」を足す（画面のメッセージを変えたら同じ PR で直す決まり）。
- `docs/PROGRESS.md`: セッションの終わりに更新する。

### やらないこと
- 自動で使わないにする（最後に使った日・期間で判定する）こと（Q2 の B・C）
- ルートに「使う期間」を持たせ、日付ごとに選択肢を変えること
- 並べ替え・よく使う順（Q8）
- 削除の条件・確認の文言を変えること（Q6）
- 記録の表示に「使わない」「削除済み」の印を付けること（U7 のまま）
- backend で、使わないルートでの出勤の保存を断ること（Q4）
- 使わないルートの編集（戻してから編集する）
- 複数のルートをまとめて使わないにする操作

### 受け入れ条件
1. ルートの一覧で「使わない」を押すと、そのルートは使うルートの一覧から消え、「使わなくなったルート（N件）」の中に出る。画面を読み直しても同じ（DB に残る）。
2. 使わないルートは、日の編集パネルの出勤のボタン、一括設定のルートの選択、追加の移動の「登録済みのルートから選ぶ」に出ない。
3. 「使うに戻す」を押すと、元の一覧と上の3か所に、また出る。名前・区間・運賃・経路の URL は変わっていない。
4. 使わないルートで出勤にしていた日は、カレンダー・表・月の合計・CSV の表示と金額が、使わないにする前と同じ。
5. その日の編集パネルを開くと、そのルートのボタンが今の選択として出る。そのまま追加の移動を足す・直すことができる。
6. `PUT /api/daily-records/:date` に使わないルートの `routeId` を送ると、200 で保存される（400 にならない）。
7. `POST /api/routes/:id/archive` を2回送っても 200 で、`archivedAt` は1回目の日時のまま。`unarchive` も2回送って 200。無い id は 404「ルートが見つかりません」。
8. 使わないルートを `PUT /api/routes/:id` で編集しても（API で直接）、使わないのまま。返る本文にも `archivedAt` がある。
9. 使わないルートを削除できる。削除しても記録の表示は変わらない（今と同じ）。
10. version 3 までの DB で backend を起動すると、migration 4 が当たり、既存のルートはすべて「使う」として出る。
11. テスト: 分ける純粋関数・repository（archive/unarchive/update で列が保たれる/migration）・router（200・404・冪等）・`initialBulkForm`（使うルートの先頭）・日の編集パネルの選択肢を作る関数（使わないルートは、今の選択のときだけ出る。`buildOptions` は関数として外に出してテストする）。
12. `npm run typecheck && npm run lint && npm run test` が通る。`openapi.test.ts` が通る。

## 4. 作業の分け方の案（1つの作業 = 1ブランチ = 1 PR）

Epic「使わなくなったルートを片付ける」の下に Task を作る。

| # | Task | 自動マージ |
|---|---|---|
| T1 | 要件定義（F1・§5・U11）と ADR-0004 | しない（要件定義・ADR） |
| T2 | shared の型と分ける関数・migration 4・repository・API・`openapi.yaml`・`troubleshooting.md`（API の部分） | しない（DB のスキーマ） |
| T3 | ルートの一覧の画面（使わない・戻す・畳んだ一覧）・`troubleshooting.md`（画面のメッセージ） | する |
| T4 | 選択肢から外す（日の編集パネル・一括設定・追加の移動） | する |

T2 は T1 のマージの後（要件と ADR が決まってから）。T3・T4 は T2 の後で、どちらが先でもよい。
