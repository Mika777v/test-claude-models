# SPEC: 使わなくなったルートを片付ける

## 0. 依頼

> 転勤で使わなくなったルートがいくつかあり、ルートの一覧と、出勤を選ぶときの選択肢がごちゃごちゃしてきた。使わなくなったルートを片付けられるようにしてほしい。

## 1. いまの状態（調べたこと）

- ルートの**削除はすでにある**（F1、`DELETE /api/routes/:id`、`RoutesPage.tsx` の削除ボタン＋確認）。過去の記録はコピーを持つので消えても金額・区間は変わらない（U7、`daily_records.route_*` に外部キー無し）。
- それでも「片付けたい」と言っているので、削除では足りない理由があるはず（下の確認事項 Q1）。削除は元に戻せず、運賃・`searchUrl` も失う。
- ルートが出る場所は3つ。いずれも「全ルート」を出している。
  1. ルート管理画面の一覧（`RoutesPage.tsx`）
  2. 日の編集パネルの「出勤（ルート名）」の選択肢（`DayPanel.tsx` の `buildOptions`）。**いま記録にあるルートが一覧に無ければ、その選択肢だけ足す**作りになっている（削除済みルート対応）
  3. 一括設定ダイアログのルート選択（`BulkDialog.tsx`）と、追加の移動の「ルートから選ぶ」（`ExtraTrips.tsx`）
- `routes` テーブルは version 1・3 まで。「使わない」を表す列は無い。

## 2. 確認事項（オーナーに確かめること）

| # | 確認すること | 選択肢 | おすすめ | 理由 |

## 3. 要件（おすすめを採用）

### やること

1. **ルートに「使わない」状態を持たせる**（アーカイブ）。ルートの項目に `archived: boolean` を足す（DB は `routes.archived_at TEXT`、NULL なら使う。値は日時のほうが「いつ片付けたか」も残り、`boolean` より情報が多い。API では `archived: boolean` で返す。ADR で決める）。
2. **ルート管理画面**
   - 各ルートに「使わない」ボタン（確認ダイアログは出さない。戻せるため）。
   - 「使わない」ルートは、一覧の下の折りたたみ「使わないルート（N件）」に移る。0件なら出さない。
   - そこでは「戻す」「編集」「削除」ができる（Q6）。
   - 削除の確認文言は今のまま。
3. **選択肢から外す**: 日の編集パネルの出勤、一括設定のルート選択、追加の移動の「ルートから選ぶ」には、使うルートだけを出す。
4. **既存の記録は変えない**（F1・U7）。日の編集パネルでは、いまの記録のルートが「使わない」でも、その記録の選択肢としては残す（`buildOptions` が今やっている削除済みルートへの対応と同じ）。
5. **API**
   - `GET /api/routes` は全ルートを `archived` 付きで返す（絞り込みは画面側。ルートは数件で、サーバーで分ける必要が薄い）。
   - `POST /api/routes/:id/archive`・`POST /api/routes/:id/unarchive`（冪等。無ければ 404 `ルートが見つかりません`）。`PUT /api/routes/:id` は `archived` を変えない（編集が状態を巻き込まないように）。
   - 日の記録の保存・一括登録で、`archived` なルートの `routeId` を新しく選ぶと 400（`workStyle.routeId`、メッセージは「選んだルートは使わない設定になっています」）。**同じ日の記録がすでに同じルートを使っている場合の再保存**は許可する。
6. **ドキュメント**（同じ PR で）: `docs/api/openapi.yaml`（`openapi.test.ts` が「メソッド＋パス」の一致を見る）、`docs/troubleshooting.md`（新しい 400 のメッセージ）、`docs/requirements.md`（F1 と決定の記録 U11）、ADR（下）、`docs/PROGRESS.md`。

### やらないこと

- 記録の金額・区間・ルート名の変更、過去の記録への印付け。
- 複数ルートをまとめて「使わない」にする操作（件数が少ない。必要なら後で）。
- 「使わない」の自動判定（最後に使った日からの経過など）。
- ルートの並べ替え、フォルダ分け、タグ。
- 削除の動作の変更（今のまま）。

### 戻しにくい変更（要確認）

| 変更 | 内容 | 扱い |
|---|---|---|
| DB のスキーマ | マイグレーション v4: `ALTER TABLE routes ADD COLUMN archived_at TEXT;`。既存の行は NULL＝使う。v1〜3 は書き換えない | **ADR を書く**（0004）。**オーナーが読んでからマージ**（自動マージしない） |
| 要件定義 | F1 に「使わなくなったルートは『使わない』にして隠せる。戻せる」、決定の記録に U11 を足す | **オーナーの確認が必要**（自動マージしない） |
| 共有の型 | `Route` に `archived: boolean`（`RouteInput` には入れない）。`RouteSnapshot` は変えない | 通常の PR でよいが、上と同じ PR にまとめる |

マイグレーションは列を足すだけで、古いコードに戻しても `SELECT` に列名を書かないので動く。ただし一度 `archived_at` を入れたデータを古い版に戻すと「使わない」が失われる（隠したルートが再び出る）。これは ADR に書く。

## 4. 受け入れ条件

1. ルート管理画面で「使わない」を押すと、そのルートが一覧の「使わないルート」に移り、メッセージ「『◯◯』を使わないルートにしました」が出る。
2. 「使わないルート」で「戻す」を押すと、元の一覧に戻る。リロードしても状態が保たれる（DB に入っている）。
3. 日の編集パネルの出勤の選択肢、一括設定のルート選択、追加の移動の「ルートから選ぶ」に「使わない」ルートが出ない。使うルートが0件のときは今の「ルートがありません」の案内が出る。
4. 「使わない」にしたルートを使っている過去の記録は、金額・区間・ルート名・合計・CSV が変わらない。その日の編集パネルを開くと、その記録のルートが選択肢に残っていて選ばれている。
5. 使うルートが1つ以上あれば、一括設定の最初のルートの選択は使うルートの先頭になる（`initialBulkForm`）。
6. API: `archived` なルートを `routeId` に指定した日の記録の保存・一括登録は 400。同じ日の記録がすでにそのルートで、同じ値で保存し直す場合は 200。存在しない ID の archive/unarchive は 404。冪等であること。
7. `PUT /api/routes/:id` で編集しても `archived` は変わらない。
8. 既存の DB（v3）を起動すると v4 が適用され、既存のルートはすべて「使う」。
9. テスト: ルートのリポジトリ（archive/unarchive/list/PUT で保持）、ルーターの archive/unarchive、日の記録の拒否と許可、`buildOptions`・`initialBulkForm` の絞り込みを Vitest で追加。`npm run typecheck && npm run lint && npm run test` が通る。
10. `docs/api/openapi.yaml` が更新され、`openapi.test.ts` が通る。
