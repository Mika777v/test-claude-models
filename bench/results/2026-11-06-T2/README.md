## 1回目でわかったこと

1. **前の作業が残した物を、後の AI はルールを知らなくても真似た。** 続きの AI にはルールの文書も案内も無いのに、前の作業がルールありだった方では、Conventional Commits のコミットとタイトル、`feat/…` のブランチ、前の PR と同じ見出しの PR 本文を書き、要件定義の変更を「確認が必要な項目」に申告した。PROGRESS.md・手順書・教科書も、前の作業が直していたので同じように直した。見本になったのは、コミットのメッセージ（= 前の PR の本文）と、リポジトリに残っていた文書
   - PR 本文の見出しは、どちらの条件も前の PR とまったく同じ並びだった（ルールありの土台: 概要・変更内容・確認が必要な項目・動作確認の方法・チェックリスト。ルールなしの土台: 概要・変更内容・自分で決めたこと・確認したこと・受け入れ条件）。後の AI は、`git log` で見えた前の PR の本文を見本にしている
2. **前の作業がルールなしだった方では、形も申告も引き継がれなかった。** 要件定義を変えた（決定の記録 U12 を足した）のに申告は無く、自動マージなら人が見ないまま入る
3. **正しさ・費用はほぼ同じ。** どちらも 18/18、直し漏れも無し。トークンは前の作業がルールありの方が約1.06倍。文書が多くても、続きの作業がほとんど重くならなかった
4. **判断の中身は同じだった。** どちらも「上限を下げる前に保存した 101 文字以上のメモは消さずに残す」「メモの行の金額は 0 ではなく空」「決定の記録は書き換えずに U12 を足す」と決め、PR に書いた
5. 前の作業がルールなしだった方は、手順書・教科書を直していないが、直し漏れではない。そもそも前の作業がメモのことを書いていなかった（文書の抜けがそのまま続く）

つまり、ルールの効果はその回だけで終わらず、**残った文書とコミットのメッセージを通して、ルールを知らない次の AI にも引き継がれる**。逆に、ルールなしで始めたリポジトリは、後からルールの無い AI が作業しても形がそろわない。

## 採点の注意

- `leftover_files`（作業の後も「200 文字」と書いてあるファイルの数）は、ルールありが 1・ルールなしが 2 だが、残っているのはどちらも要件定義の決定の記録（「200 文字から 100 文字にする」）と、API の仕様書の説明（「200 文字から下げる前に保存した長いメモはそのまま返る」）で、直し漏れではない。正解の実装を当てても 1 になる。この判定は、決定の記録などを除かないと差を見分けない
- 前の作業がルールありの方の `out_of_scope=1` は、ルートの `README.md`（CSV の節にメモの行を足した）。妥当な変更で、`SCOPE_RE` に `README.md` が入っていないための判定
- 「ブランチ・コミット・PR の形」の判定（`branch_named`・`commits_conventional`・`pr_title_ok`）は、ルールの文書が無い条件でも同じ基準で見ている。PR の見出し（`pr_sections_ok`）は、続きの作業場所に PR テンプレートが無いので採点していない（上の表の「前の PR と同じ見出し」は読んで確かめた）
