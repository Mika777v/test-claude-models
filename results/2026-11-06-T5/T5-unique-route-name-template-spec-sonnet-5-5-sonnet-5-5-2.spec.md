# SPEC: 同じ名前のルートを登録できないようにする

## 1. 背景と現状（調べたこと）

- `POST /api/routes`（`backend/src/routes/route-router.ts`）は、`parseRouteInput` の検証だけで `repo.create` する。名前の重複は見ていない。
- `name` は `text()`（`backend/src/validation/fields.ts`）で前後の空白を取り除いた値になる。
- `routes` テーブル（`backend/src/db/migrations.ts`）に `name` の UNIQUE は無い。`RouteRepository` に名前で探す口も無い。
- フロントは、失敗の応答が `ApiError` の形なら、ステータスに関係なく `fieldErrors` を `toRouteFormErrors` で欄ごとに振り分け、`field: "name"` はルート名の欄の下に出す（`frontend/src/api-client.ts` / `RouteForm.tsx`）。**409 でも今の仕組みでそのまま出るはず**。ただし 409 でも出ることをテストで確かめる。
- 出勤の記録は、ルートの値をコピーして持つ（`daily_records.route_name` など）。ルート名の重複を禁じても、過去の記録は影響を受けない。
- `docs/api/openapi.yaml` の `POST /api/routes` に 409 が無い。`docs/troubleshooting.md` の「API のステータス」表にも 409 が無い（CLAUDE.md の決まりで同じ PR で直す）。

## 2. オーナーに確かめること（あいまいな点）

各項目の「おすすめ」を採用したものとして、§3 以降を書いている。

### Q1. ルートの編集（`PUT /api/routes/:id`）でも、他のルートと同じ名前への変更を止めるか
- 選択肢
  - A. 止める（自分自身の名前のまま保存するのは許す）
  - B. 登録（POST）だけ止める。編集は今のまま
- **おすすめ: A**
- 理由: 困りごとは「一覧に同じ名前が2つあって選べない」こと。編集で同じ名前にできると、登録で止めても同じ状態になる。Task の作業内容は POST だけを書いているので、**依頼の範囲を少し広げる判断**になる。編集画面も同じ `RouteForm` なので、画面の変更はほぼ増えない。

### Q2. 「同じ名前」の判定の厳しさ
- 選択肢
  - A. 前後の空白を取り除いた後の完全一致（今の保存の値でそのまま比べる）
  - B. A に加えて、全角・半角、英字の大文字小文字の違いも同じとみなす（例: `Ａ駅↔本社` と `A駅↔本社`）
  - C. 見た目が似ているものまで広く判定する（記号の揺れなど）
- **おすすめ: A**
- 理由: 利用者は本人1名で、同じ文字で重複を作る失敗を防げば足りる。B・C は「違う名前のつもりが弾かれる」誤判定の説明が要り、ルールも増える。必要になったら足す（その場合は判定を 1 つの関数に閉じ込めてあるので直しやすい）。

### Q3. 重複をどこで防ぐか（DB の UNIQUE 制約を付けるか）
- 選択肢
  - A. API（アプリ）で、保存の前に同じ名前があるか調べる。DB のスキーマは変えない
  - B. A に加えて、DB に `UNIQUE (user_id, name)` を足す（マイグレーション v4）
- **おすすめ: A**
- 理由:
  - B は**戻しにくい**変更（スキーマ・マイグレーション。`needs-confirm`、自動マージしない、ADR も必要）。
  - 今の DB に「自宅↔本社」が 2 つある可能性が高い（Task のきっかけ）。UNIQUE の追加は、既存の重複を先に直さないと**失敗してアプリが起動しなくなる**。データの移し方も決める必要がある。
  - 利用者は1名、`node:sqlite` は同期 API なので、「調べる→保存する」の間に別の書き込みは割り込めない。アプリでの確認で十分。
  - DB の制約が必要になったら、既存データの整理方針と一緒に別 Task にする。

### Q4. すでにある重複ルート（今の DB の 2 つの「自宅↔本社」）をどうするか
- 選択肢
  - A. 何もしない（自動で消さない・名前を変えない）。オーナーが画面から編集・削除して直す
  - B. マイグレーションで自動的に別名にする（例: 「自宅↔本社 (2)」）
  - C. 画面に「重複があります」と警告を出す
- **おすすめ: A**
- 理由: 自動で名前を変えると、どちらがどのルートか分からなくなり、データを勝手に書き換える。B はスキーマ/データの変更で戻しにくい。C は今回の依頼の外。既存の重複の片方は、Q1=A の編集機能で名前を変えれば直せる（重複のまま保存する場合は 409）。
- 補足: 重複したままの 2 つのうち片方の**他の項目だけ**を編集するときは、自分の名前が他と同じなので 409 になる。このときは、名前を変えて保存すればよい。この動きを troubleshooting にも書く。

### Q5. エラーメッセージの文と欄の割り当て
- Task の指定どおり: 外側の `error` は「入力に誤りがあります」（今の 400 と同じ）、`fieldErrors` は `[{ field: "name", message: "同じ名前のルートがあります" }]`。
- 確認したいこと: `error` の文を「同じ名前のルートがあります」にしてもよいが、おすすめは**今の 400 と同じ文のまま**（Task に「今のエラーと同じ形」とある。フロントは `fieldErrors` があれば `error` の文を使わない）。

### Q6. 他のユーザーのルートとの扱い
- 今は固定の 1 ユーザーだけ。ただし将来の複数ユーザーに備え、**同じ `userId` の中での重複**を判定する（他の人の同名ルートは許す）。おすすめどおりで特に確認は要らない。

## 3. やること

### 3.1 backend
1. `RouteRepository` に、名前でルートを探す口を足す。例: `findByName(userId, name): Route | undefined`（編集用に「自分以外」を除ける形にする。例: `findByName(userId, name, exceptId?)`）。`SqliteRouteRepository` に実装する。
   - 比較は Q2=A（保存されている `name` との完全一致。`parseRouteInput` で空白は取り除き済み）。
   - SQL は `WHERE user_id = ? AND name = ?`（`exceptId` があれば `AND id <> ?`）。
2. `POST /api/routes`: 検証（400）を通った後、同じ名前があれば登録せずに **409** を返す。
   ```json
   { "error": "入力に誤りがあります",
     "fieldErrors": [{ "field": "name", "message": "同じ名前のルートがあります" }] }
   ```
   - 検証の誤り（400）と重複（409）が両方あるときは、先に **400** を返す（形が正しくない入力は重複を見る前に弾く）。
3. `PUT /api/routes/:id`（Q1=A）: 検証の後、**自分以外**に同じ名前があれば 409（同じ本文）。対象の id が無いときは、これまでどおり 404（404 を重複の確認より先にする: 存在しない id では 404）。
4. 文言は定数 1 か所に置く（router 内でもよい）。`ApiError` の型（`shared/src/api.ts`）は変えない。
5. `docs/api/openapi.yaml`: `POST /api/routes` と `PUT /api/routes/{id}` に `409` を足す（例つき）。`components/responses` に `Conflict` を足してよい。

### 3.2 frontend
- 実装の変更は原則なし（`fieldErrors` の `name` は既に欄の下に出る）。
- **確かめること**: 409 でも、`api-client` が本文を `ApiError` として返し、`toRouteFormErrors` で `name` の欄の下に出る。出なければ直す。
- 重複エラーの後、名前を直して再送信すれば登録できること（古いエラーが残らない。今の 400 と同じ動き）。

### 3.3 テスト（Vitest）
- `route-router.test.ts`: 
  - 同じ名前の POST → 409、本文が上の形、`GET /api/routes` の件数が増えない
  - 違う名前の POST → 201
  - 前後に空白がある同じ名前（`" 自宅↔本社 "`）→ 409（Q2=A でも保存前に空白を取り除くため）
  - 400 の入力（名前が空など）→ 400 のまま
  - PUT: 他のルートと同じ名前 → 409、自分の名前のまま他の項目を直す → 200、存在しない id → 404
  - 削除した後は、同じ名前で登録できる
- `sqlite-route-repository.test.ts`: `findByName` が、同じ `userId` の同じ名前だけを返す・`exceptId` で自分を除く・他の `userId` のルートは返さない
- フロントのテスト（既存の `routes-api.test.ts` / `route-form.test.ts` の並び）: 409 + `fieldErrors` が `ApiResult` の失敗として返り、`toRouteFormErrors` で `name` に入る
- `npm run typecheck && npm run lint && npm run test` を通す

### 3.4 ドキュメント（同じ PR で）
- `docs/troubleshooting.md`:
  - 「画面のメッセージ」の表に「同じ名前のルートがあります（ルート名の欄の下）」を足す。原因: 同じ名前のルートが既にある（409）。対処: 名前を変える、または既存のルートを編集・削除する。既存の重複ルートの片方を編集して名前が変わらないと保存できない旨も書く。
  - 「API のステータス」の表に **409** を足す（`backend/src/routes/route-router.ts`）。
- `docs/api/openapi.yaml`（§3.1-5）
- `docs/PROGRESS.md`（セッションの終わりに更新）

## 4. 要件定義・ADR・スキーマの扱い

- **DB のスキーマは変えない**（Q3=A）。マイグレーションを足さない。
- **`docs/requirements.md` の F1（ルート管理）に「ルート名は重複できない」と1行足すのがよい**。これは**要件定義の変更なので、自動マージせずオーナーに確認する PR**（CLAUDE.md・DEV_RULES）。実装の PR に含めるか、確認待ちの別 PR に分けるかは、オーナーが決める（おすすめ: 実装 PR は自動マージできるよう要件定義の変更を含めず、`docs/requirements.md` の1行は別 PR）。
  - 追加する文の案: 「ルート名は、同じ人の中で重複できない（前後の空白を除いた完全一致で判定する）。」
- ADR: 今回の判断（アプリで確認する・DB の UNIQUE にしない）は、**戻しやすい**ので ADR は不要と考える。ただし、後で DB の UNIQUE 制約へ進めるときは ADR とマイグレーションの PR が要る（既存の重複データの扱いと一緒に）。ADR を書くかどうかはオーナーが決める。
- API の 409 の追加は、フロント・バックの契約の追加（`ApiError` の型は不変、ステータスが増える）。既存の呼び出し元（400 を前提にした分岐）が無いことは調べ済み（フロントはステータスを見ずに本文を使う）。

## 5. やらないこと
- DB の UNIQUE 制約・マイグレーション（Q3）
- 既存の重複データの自動修正・警告表示（Q4）
- 全角・半角、大文字小文字などの「ゆるい」重複判定（Q2）
- 一括設定・日次記録・追加の移動（`source_route_id`）の変更。ルートの一覧・削除・出勤の保存の動きは変えない
- 画面の見た目の変更、ルート名の入力中のリアルタイムな重複チェック（送信したときに 409 で知らせる）

## 6. 受け入れ条件
- [ ] すでにある名前でルートを `POST` すると 409。本文は `error: "入力に誤りがあります"`、`fieldErrors: [{ field: "name", message: "同じ名前のルートがあります" }]`。ルートは増えない
- [ ] 前後に空白がついた同じ名前でも 409
- [ ] 違う名前なら今までどおり 201 で登録できる
- [ ] 入力の形が誤っているものは、今までどおり 400
- [ ] （Q1=A）`PUT` で他のルートと同じ名前にすると 409、自分の名前のままの編集は 200、無い id は 404
- [ ] 画面の登録フォームで、重複の文が**ルート名の欄の下**に、他の入力の誤りと同じ見た目で出る（フォーム上部の警告には出ない）。名前を直して再送信すれば登録できる
- [ ] ルートの一覧・削除・出勤の保存・過去の記録の金額/ルート名は変わらない（既存のテストがすべて通る）
- [ ] DB のスキーマ・マイグレーション・`shared/` の型に変更が無い
- [ ] `docs/api/openapi.yaml` と `docs/troubleshooting.md` が更新されている
- [ ] `npm run typecheck && npm run lint && npm run test` が通る

## 7. 進め方の注意
- PR は 1 本（`feat(routes): …` など `pr-title.yml` の type・scope に合わせる）、本文に `Closes #<Task>`。
- 実装 PR が §4 の方針（スキーマ・要件定義に触れない）を守るなら、自動マージの対象。`docs/requirements.md` を含める場合は「確認が必要な項目」に書き、自動マージを予約しない。
