# SPEC: 同じ名前のルートを登録できないようにする

状態: オーナー確認前（下の「確かめること」のおすすめを採用した前提で書いている）

## 1. 背景

ルートの一覧に「自宅↔本社」が2つあり、出勤を選ぶときにどちらか分からなくなった。名前は画面で区別する唯一の手がかりなので、同じ名前を持てないようにする。

## 2. 調べたこと（現状）

- `POST /api/routes` は `backend/src/routes/route-router.ts`。`parseRouteInput` で検証し、通れば `repo.create` で登録する。名前の重複は見ていない。
- `PUT /api/routes/:id` も同じ検証だけで、重複は見ていない。
- `parseRouteInput`（`validation/fields.ts` の `text`）はルート名の前後の空白を取り除き、最大文字数を見る。
- `routes` テーブル（`backend/src/db/migrations.ts` のバージョン1〜3）に名前の一意制約は無い。`RouteRepository` に名前で探す口も無い。
- 画面は `frontend/src/routes/RouteForm.tsx`。`toRouteFormErrors` が `fieldErrors` を欄ごとに分け、`field: "name"` の文をルート名の欄の下（`field-error`）に出す。**409 でも `api-client.ts` の `request` は本文の `ApiError` をそのまま返すので、画面側の出し方は 400 と同じで動く見込み**（実装時に確かめる）。
- `docs/api/openapi.yaml` の `POST /api/routes` に応答は 201 と 400 だけ。`docs/troubleshooting.md` のステータス表にも 409 は無い。
- 日次記録は、記録した時点のルート名をコピーして持つ（`route_name`）。ルートの名前の重複は過去の記録に影響しない。

## 3. 確かめること（オーナーへ）

### Q1. 編集（`PUT /api/routes/:id`）でも同じ名前を弾くか
- 依頼は「登録（POST）」だけ書いている。しかし編集で別のルートと同じ名前に変えられると、同じ問題が起きる。
- 選択肢:
  - A. POST だけ弾く（依頼どおり）
  - B. POST と PUT の両方で弾く。PUT は自分自身の名前のままなら通す
- **おすすめ: B**。理由: 目的は「出勤を選ぶときに区別できる」こと。PUT が抜け道のままだと目的を果たせない。
- 注意: 受け入れ条件3「編集…の動きは変わらない」は「重複しない編集は今までどおり」と読む。重複する名前への変更だけが新しく 409 になる。

### Q2. 「同じ名前」の判定の厳しさ
- 選択肢:
  - A. 完全一致のみ（前後の空白は既に取り除かれる）
  - B. 全角/半角（NFKC）・英大小文字の違いも同じとみなす（例: `Home↔本社` と `home↔本社`）
- **おすすめ: A**。理由: 依頼は「同じ名前」。過剰に弾くと、別物のつもりのルートが登録できず戸惑う。ただし前後の空白は既存の `text` で取り除かれるので、「自宅↔本社 」も同じ名前として弾かれる。B にしたくなったら後から足せる。

### Q3. DB に一意制約（UNIQUE インデックス）を足すか
- 選択肢:
  - A. API（アプリのコード）だけで判定する。DB は変えない
  - B. A に加えて、`routes` に `UNIQUE (user_id, name)` を新しい migration（バージョン4）で足す
- **おすすめ: A**。理由:
  - 使うのは1人・1プロセスで、`node:sqlite` は同期なので「探す → 登録」の間に割り込まれない。競合の心配が小さい。
  - **B は戻しにくい**。すでに同名のルートがある DB（依頼の発端そのもの）では、migration が失敗して backend が起動しなくなる。先に既存データを直す（名前を変える・消す）手順が要る。CLAUDE.md の規則どおり、DB のスキーマ変更と ADR が要り、オーナー確認の PR になる。
  - 将来、複数ユーザー化・DB 差し替えのときに B（`user_id` と名前の一意）を足せば足りる。
- 採用した A の結果: DB のスキーマは変えない。ADR も不要（後から変えにくい決定ではない。ただし実装者は、A にした理由を PR の本文に短く書く）。

### Q4. すでにある同名のルート（依頼の発端のデータ）をどうするか
- 選択肢:
  - A. 何もしない。オーナーが画面で名前を直すか、片方を消す
  - B. migration で自動的に名前を変える（例: 「自宅↔本社 (2)」）
- **おすすめ: A**。理由: どちらを残すかは本人しか分からない。自動で名前を書き換えるのは戻しにくい。既存の同名ルートは、そのまま一覧に出て、編集・削除もできる（Q1 の B だと、片方の名前を変えるときは新しい名前が他と重ならなければ通る。名前を変えずに他の欄だけ直すのも、自分以外に同名が残っていると 409 になる点に注意 → 次のQ5）。

### Q5. 同名が既にある 2 つのうち 1 つを、名前を変えずに編集したら（Q1=B のとき）
- 選択肢:
  - A. 名前が変わっていなくても、他に同名があれば 409
  - B. 名前を変えていないなら（自分の今の名前と同じ）、他に同名があっても通す
- **おすすめ: A**。理由: 実装が単純で規則が一貫する（「同名のルートが 2 つ以上になる保存は通さない」）。直すには名前を変えればよく、メッセージもそれを促す。B にすると既存の重複が残ったまま放置されやすい。
- 補足: 実装は「自分以外（id が違う）に同名があれば 409」。

### Q6. 文言・本文の形
- 依頼で決まっている: ステータス 409。本文は `{ error, fieldErrors: [{ field: "name", message: "同じ名前のルートがあります" }] }`。
- 未決: `error`（全体の文）。**おすすめ: 既存と同じ「入力に誤りがあります」**。理由: 依頼が「今のエラーと同じ形」と言っており、画面の既存の出し方（`fieldErrors` を欄に出す）をそのまま使える。

## 4. 要件（おすすめを採用した前提）

### やること

1. **ルートの登録（`POST /api/routes`）**
   - 検証（400）を通った後、同じユーザーの既存ルートに、名前が同じもの（Q2=完全一致。検証後の、前後の空白を除いた値で比べる）があれば、登録せずに 409 を返す。
   - 本文: `{ "error": "入力に誤りがあります", "fieldErrors": [{ "field": "name", "message": "同じ名前のルートがあります" }] }`
   - 入力の誤り（400）と重複（409）が同時にあるときは 400 を優先する（重複の判定は検証を通った後）。
2. **ルートの編集（`PUT /api/routes/:id`）**（Q1=B）
   - 自分以外（id が違う）のルートに同じ名前があれば、更新せずに 409（本文は上と同じ）。自分の名前のままで他の欄だけを変える編集は通る（他に同名が無い場合）。
   - 順序: 400 → 404（対象が無い）→ 409。存在しない id は、重複より先に 404 とする。
3. **判定の置き場所**
   - 重複の判定は `RouteRepository` に口を足して行う（例: `findByName(userId, name)`、または `existsByName(userId, name, exceptId?)`）。API は SQLite を知らないままにする（`route-repository.ts` の方針）。SQLite 実装とそのテストも足す。
   - 判定と登録/更新は同期処理で続けて行う（Q3=A の前提）。
4. **画面**
   - 登録・編集のフォームで 409 が返ったら、「同じ名前のルートがあります」をルート名の欄の下に出す（今の入力の誤りと同じ出し方: `field-error`、`aria-invalid`、`aria-describedby`）。フォームの入力値は残し、そのまま名前を直して再送できる。
   - 画面側の処理が既に 409 を扱えるなら、コードの変更は不要でもよい。ただしテストは足す（下記）。
5. **文書（同じ PR で直す。CLAUDE.md の規則）**
   - `docs/api/openapi.yaml`: `POST /api/routes` と `PUT /api/routes/{id}` に 409 を足す（共通の `Conflict` 応答を作り、例を付ける）。`openapi.test.ts` が通ること。
   - `docs/troubleshooting.md`: 「画面に出るメッセージ」に「同じ名前のルートがあります」（原因: 同名のルートが既にある。見る場所: `backend/src/routes/route-router.ts`）、「API のステータス」に 409 を足す。
   - `docs/requirements.md` の F1 に「ルート名は、同じ人のルートの中で重ならない」を 1 行足す。これは要件定義の変更なので、**オーナー確認の PR にする**（CLAUDE.md の規則）。`更新日` も更新する。
   - `docs/PROGRESS.md` を更新する。

### やらないこと

- DB のスキーマ変更（UNIQUE 制約・migration）をしない。ADR も書かない（Q3=A）。
- すでにある同名のルートの自動的な改名・統合・削除をしない（Q4=A）。
- 大文字小文字・全角半角を同じとみなす判定をしない（Q2=A）。
- ルートの一覧・削除、日次記録（出勤の保存・一括設定）の動きを変えない。過去の記録がコピーしたルート名は変わらない。
- 画面でのリアルタイムの重複チェック（入力中に出す）はしない。送信後の応答で出す。
- 経路検索（`/api/route-search`）の変更はしない。

### 受け入れ条件

依頼の 3 つに、次を加える。

- [ ] すでにある名前でルートを登録しようとすると 409 で、本文が上の形になり、ルートは増えない（`GET /api/routes` の件数が変わらない）
- [ ] 違う名前なら、今までどおり 201 で登録できる
- [ ] 前後に空白を付けた同じ名前（`" 自宅↔本社 "`）も 409
- [ ] 名前が空などの入力の誤りは今までどおり 400（重複の判定より先）
- [ ] 別のルートと同じ名前に編集すると 409 で、ルートは変わらない。名前を変えずに他の欄だけ変える編集（他に同名が無いとき）は 200
- [ ] 存在しない id の PUT / DELETE は今までどおり 404
- [ ] ルートの一覧・削除、出勤の保存、一括設定の動きは変わらない（既存のテストが通る）
- [ ] 画面: 409 のとき、ルート名の欄の下に「同じ名前のルートがあります」が出る。他の欄の入力は残る。名前を直して再送すると登録できる
- [ ] 文書: openapi.yaml・troubleshooting.md・requirements.md F1 が更新されている
- [ ] テスト: route-router（POST/PUT の 409・400 優先・404 優先）、SQLite リポジトリの重複判定、フロント（409 の `fieldErrors` が name 欄に割り当てられること。`route-form.test.ts` / `routes-api.test.ts`）
- [ ] `npm run typecheck && npm run lint && npm run test` が通る

## 5. 戻しにくい変更・オーナー確認が要る点

- **要件定義（`docs/requirements.md` F1）の変更を含む** → CLAUDE.md の規則で、自動マージせずオーナーに確認する PR。PR 本文の「確認が必要な項目」に書く。
- **DB のスキーマは変えない**（Q3=A）ので、データを戻せなくなる変更は無い。もし Q3 で B（UNIQUE 制約）を選ぶなら、戻しにくい変更になる: 既存の同名ルートを先に直す手順、migration（バージョン4。既存の番号の SQL は書き換えない）、ADR、オーナー確認の PR が必要。そのときは、このSPECを改めて書き直す。
- API の新しいステータス（409）の追加は、後から消しにくい API の形の決定だが、依頼で指定済みなので ADR は不要と考える（ADR-0003 の OpenAPI に反映すれば足りる）。

## 6. 作業の単位

- Issue（Task）に紐づけ、1 ブランチ・1 PR。Conventional Commits のタイトル（例: `feat(routes): 同じ名前のルートの登録を 409 で弾く`。type・scope は `pr-title.yml` で確認）。本文に `Closes #Task`。
- 編集（Q1=B）を実装に含めるのが大きすぎる場合は、POST と PUT を分けて 2 PR にしてよい（先に POST）。
