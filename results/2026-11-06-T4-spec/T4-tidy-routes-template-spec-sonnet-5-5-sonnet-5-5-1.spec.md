# SPEC: 使わなくなったルートを片付ける

- 対象 Task: 「使わなくなったルートを片付けたい」（転勤で使わなくなったルートが、ルートの一覧と出勤の選択肢に残ってごちゃごちゃする）
- 状態: 要件案（オーナーに確認する前。下の「確認事項」の**おすすめを採用したもの**として書いてある）
- このファイルは実装する人への引き継ぎ用。コードや既存の文書は、まだ変えていない

---

## 0. 調べて分かったこと（先に読む）

1. **ルートの削除は、もう作ってある。** 要件定義 F1 に「削除」があり、`DELETE /api/routes/:id`、`RoutesPage.tsx` の削除ボタン、確認ダイアログ（「作成済みの記録の金額と区間は変わりません」）まで動く。決定 U7 のとおり、削除したルートを使っていた記録はコピーした値（`RouteSnapshot`）を表示するので、**削除しても過去の記録・金額・CSV は壊れない**。
2. つまり「ごちゃごちゃを片付ける」だけなら、**今でも1件ずつ削除すれば済む**。それでもこの Task が出たので、削除では足りない理由があるはず（確認事項 Q1）。考えられるのは次の2つ。
   - 削除は**戻せない**（ルート名・出発地・到着地・運賃・経路の URL が消える）。転勤で戻る、似たルートをまた使う、運賃の根拠を残しておきたい、などで消したくない。
   - 削除ボタンがあることに気づいていない／何件も消すのが面倒。
3. 出勤を選ぶ画面は3か所で、どれも `GET /api/routes` の全件から選択肢を作っている（`DayPanel.tsx` の `buildOptions`、`BulkDialog.tsx`、追加の移動の `ExtraTripForm.tsx`）。一覧を絞れば3か所とも減る。
4. すでに削除されたルートを使っている日の記録は、`DayPanel.tsx` の `buildOptions` が「記録のコピーの名前」で選択肢に出す作りになっている。使わなくなったルートを選択肢から外しても、**過去の日の表示は崩れない**（実装では動作確認する）。
5. バックエンドの `resolveWorkStyle`（`backend/src/daily-records/resolve-work-style.ts`）は `routes.get` が見つかれば何でも通す。「使わなくなったルート」を新しい記録に選べないようにするには、ここで弾く必要がある。

## 1. 確認事項（オーナーに聞くこと）

各項目に **おすすめ**を付けた。以降の要件は、おすすめを採用した前提。

### Q1. 「片付ける」とは何をすることか（いちばん大事）

| 選択肢 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| A. 「使わない」にする（アーカイブ） | ルートを消さずに「使わなくなったルート」にする。一覧では下の別枠に畳み、出勤・追加の移動の選択肢から外す。**元に戻せる**。削除も残す | 戻せる。一覧と選択肢が片付く。過去の記録は変わらない | DB に列を足す（スキーマ変更）。画面と API が増える |
| B. 何も足さない | 今の削除で片付ける。削除の確認文を「元に戻せません」に直すくらい | 作る物がほぼ無い。スキーマ変更なし | 戻せない。「消したくないが邪魔」は解決しない |
| C. 削除をまとめてできるようにする | 複数選んで一括削除 | 件数が多くても楽 | 戻せない。ルートは数件なので効果が小さい |

- **おすすめ: A。** 「片付けたい」の中心は、一覧と選択肢のごちゃごちゃで、消すことではない。削除は戻せず、転勤は元に戻ることもあり得る。数件のルートなので C は要らない。
- B で十分（削除に気づいていなかっただけ）ならこの Task は小さく済む。**Q1 の答えが B なら、以降は不要で、削除の確認文の修正だけ**。

### Q2. 「使わない」にしたルートの扱い

| 項目 | 選択肢 | おすすめと理由 |
|---|---|---|
| 新しい記録に選べるか | 選べない／選べる | **選べない**。選択肢から消すのが目的。API でも弾く（画面だけで隠すと、古い画面から選べてしまう） |
| 編集できるか | できる／できない | **できない**（先に「元に戻す」）。使わないルートの値を直す理由が無く、操作が減る |
| 削除できるか | できる／できない | **できる**。本当にいらなくなったら消せる（今の削除をそのまま使う） |
| 追加の移動の「ルートから選ぶ」に出すか | 出す／出さない | **出さない**。選択肢を減らすのが目的で、3か所をそろえる |
| 過去の記録・追加の移動 | 変える／変えない | **変えない**。すでにコピーを持つ（U7）。表示・金額・CSV は今のまま |

### Q3. 一覧での見せ方

| 選択肢 | おすすめと理由 |
|---|---|
| 同じ一覧に残して薄く表示 | |
| 別の枠「使わなくなったルート（N件）」を一覧の下に置き、最初は閉じておく | **これ。** 普段の一覧がすっきりし、必要なときだけ開いて「元に戻す」「削除」ができる |
| 別画面にする | 画面が増えるので不要 |

### Q4. 「使わない」にするときの確認ダイアログ

- 戻せるので**確認は出さない**（押したらすぐ。結果は「『◯◯』を使わなくなったルートにしました」と画面に出す）。削除の確認は今のまま。

### Q5. ルートが全部「使わない」になったとき

- 今の「ルートが無いので、出勤は選べません。」の文をそのまま使う。「ルートがありません」の案内で、管理画面に「使わなくなったルートがあります」と添える必要は**ない**（おすすめ。画面が増えるため）。

### Q6. すでに記録にある日の、同じ「使わない」ルートの出勤を再保存したとき

- 例: 使わなくなったルートの出勤が入っている日で、パネルに出ているその選択肢をもう一度押す。
- 選択肢: ①弾く（「このルートは使わなくなっています」） ②同じルートなら変更なしとして通す
- **おすすめ: ①。** 実装が単純で、「新しい記録には使えない」の原則が崩れない。パネルでは現在の選択肢が選択済みの表示になっているはずなので、押す場面は少ない。実装時に画面の動きを見て、不自然なら②に倒す（その場合はオーナーに報告）。

## 2. やること

### 2.1 戻しにくい変更（先に出す・オーナーが読んでからマージ）

この Task は、次の3つが「自動マージしない」対象に当たる。**実装の PR とは別に、先に文書の PR を出してオーナーに確認してもらう。**

1. **DB のスキーマの変更**: `routes` に列を足す（2.2）。`docs/GITHUB_WORKFLOW.md` §4 の対象
2. **ADR を新しく書く**: `docs/adr/0004-archive-routes.md`（後から変えにくい判断なので。`docs/adr/README.md` の表にも足す。CLAUDE.md により「迷わず決めても書く」）
   - 書くこと: 背景（削除は戻せない）／選択肢（Q1 の A・B、さらに「`archived` を真偽値の列にする」案と比べる）／決定／影響（マイグレーション4・`GET /api/routes` の既定の変更・「選べない」を API で弾く）／見直すとき
3. **要件定義の変更**: `docs/requirements.md`
   - F1 に「使わなくなったルートの片付け（アーカイブ）」を足す
   - 「5. データの項目」のルートに `archived`（真偽値）を足す
   - 「決定の記録」に **U11** を足す（「ルートは削除のほかに『使わない』にできる。戻せる。使わないルートは新しい記録・追加の移動に選べない。過去の記録は変わらない」）
   - 更新日を直す

マイグレーションの SQL は**足すだけ**（既存データを書き換えない）で、後から列を使わなくなっても害は無い。戻す手順は ADR の「影響」に書く（`archived_at` を `NULL` に戻すだけ。列の削除は不要）。

### 2.2 DB

- `backend/src/db/migrations.ts` に **version: 4** を足す（version 1〜3 は書き換えない）。

```sql
-- 使わなくなったルート。NULL なら今も使う。値があれば、使わなくした日時（ISO 8601）
ALTER TABLE routes ADD COLUMN archived_at TEXT;
```

- 今までのルートは `NULL` のまま（＝使う）。データの移行は要らない。
- 列は日時（`archived_at`）にする。真偽値より情報が多く、`created_at` / `updated_at` と書き方がそろう。API では `archived: boolean` として見せる（画面は日時を使わない）。

### 2.3 共有の型（`shared/`）

- `Route` に `archived: boolean` を足す（必須。DB の NULL は `false` に変える）。
- `RouteInput` は `Omit<Route, "id" | "userId" | "archived">` にする。登録・編集の入力に `archived` を入れない（編集で意図せず戻す・隠すことを防ぐ）。
- `RouteSnapshot` は変えない（`Pick` にそもそも含まれない）。

### 2.4 API（バリデーションは受け口で）

| メソッドとパス | 内容 |
|---|---|
| `GET /api/routes` | 既定は**使うルートだけ**返す。`?includeArchived=true` で全件（使わないものも `archived: true` で入る）。`includeArchived` が `true` / `false` 以外なら 400 |
| `PATCH /api/routes/:id` | 本文 `{ "archived": boolean }`。`true` で使わなくする、`false` で戻す。すでにその状態でも 200（べき等）。ルートが無ければ 404。`archived` が真偽値でなければ 400（`fieldErrors` に `archived`） |
| `PUT /api/routes/:id` | 使わなくなったルートに対しては **409**（`{ error: "使わなくなったルートは編集できません。先に元に戻してください" }`）。ルートが無ければこれまでどおり 404 |
| `DELETE /api/routes/:id` | 変更なし（使う・使わないに関わらず消せる） |
| 勤務区分に出勤を指定する API（`PUT /api/daily-records/:date`、`POST /api/daily-records/bulk`、`POST /api/daily-records/bulk/preview`） | `routeId` が使わなくなったルートなら **400**。`fieldErrors` は既存の `workStyle.routeId` の形で、メッセージは「このルートは使わなくなっています」（見つからないときの「選んだルートが見つかりません」とは別の文にする） |

- `RouteRepository` に `setArchived(userId, id, archived): Route | undefined` を足し、`list` は `includeArchived` を受け取る（既定は使うものだけ）。`SqliteRouteRepository` で実装する。DB の差し替えやすさ（インターフェースの後ろに隠す）を守る。
- `resolveWorkStyle` は、見つからない（今の `undefined`）と、使わなくなっている、を区別して返す。戻り値の型は判別可能なユニオン型にする（CLAUDE.md の方針）。
- 追加の移動の `sourceRouteId` は記録するだけで検証していない（今のまま）。API の変更は無し。選べなくするのは画面側（2.5）。
- `docs/api/openapi.yaml` を同じ PR で直す（`PATCH` の追加、`GET` のクエリ、`PUT` の 409、`Route` に `archived`、各 400 の説明）。`openapi.test.ts` が「メソッド＋パス」の一致を見るので、足さないとテストが落ちる。

### 2.5 画面

**ルート管理画面（`RoutesPage.tsx`・`RouteTicket.tsx`）**
- `listRoutes` を `includeArchived=true` で呼び、フロントで「使うルート」と「使わなくなったルート」に分ける。
- 使うルートの各チケットに「使わなくする」ボタンを足す（確認なし。削除の隣に置き、見た目は削除より目立たせない）。
- 一覧の下に、`<details>` などの折りたたみ枠「使わなくなったルート（N件）」を置く。0件なら枠ごと出さない。最初は閉じる。
- 枠の中の各チケットには「元に戻す」と「削除」を置く（「編集」は出さない）。削除の確認文は今のまま。
- 実行後は一覧を読み直し、結果を `notice` に出す（例: 「『自宅↔旧本社』を使わなくなったルートにしました」「『…』を元に戻しました」）。
- 編集中のルートを「使わなくする」したら、編集フォームを閉じる（削除のときと同じ）。

**月次画面（カレンダー）**
- `CalendarPage.tsx` の `listRoutes()` は既定（使うルートだけ）のままにする。これで `DayPanel`・`BulkDialog`・`ExtraTripForm` の3か所の選択肢が自動で減る。コードの変更は不要の見込み。
- 使わなくなったルートの出勤が入っている日は、これまでの削除済みと同じく、記録のコピーの名前で表示する（`buildOptions` の既存の処理。動作を確認する）。表・合計・CSV も変わらない。
- 画面に出るエラーメッセージに「このルートは使わなくなっています」が増える（Q6）。

**`docs/troubleshooting.md`（CLAUDE.md の規則で同じ PR で直す）**
- 画面のメッセージの表に「このルートは使わなくなっています」「使わなくなったルートは編集できません。先に元に戻してください」を足す（症状 → 原因 → 見る場所）。
- API のステータスの表に、409（使わなくなったルートの編集）を足し、400 の説明に「使わなくなったルートを出勤に選んだ」を足す。
- DB の説明に、`routes.archived_at` を足す。

## 3. やらないこと

- 使っていないルートの自動判定・自動で使わなくする（期間や最後に使った日で）
- ルートの複数選択・一括の「使わなくする」「削除」
- 使わなくなったルートの編集（戻してから編集する）
- 過去の記録・追加の移動の書き換え、記録の側に「使わなくなった」の印を付けること（U7 のまま、印は付けない）
- 削除の仕様変更（ごみ箱、削除の取り消し）
- 経路検索（U1）の変更。使わなくなったルートの `searchUrl` は、そのまま残す
- 認証・複数ユーザー（`userId` は今までどおり固定値）

## 4. 受け入れ条件

**ルート管理画面**
1. 使うルートの「使わなくする」を押すと、確認なしでそのルートが上の一覧から消え、下の「使わなくなったルート（N件）」に移る。N が増える。
2. 「使わなくなったルート」の枠は、最初は閉じている。0件のときは枠が出ない。
3. 枠の中のルートに「編集」は無く、「元に戻す」と「削除」がある。
4. 「元に戻す」を押すと、上の一覧に戻る。名前・区間・運賃・経路の URL は使わなくする前と同じ。
5. 枠の中の「削除」を押すと、確認のあとにルートが消え、記録の金額と区間は変わらない。
6. ブラウザを読み直しても、使う・使わないの状態が残っている。

**選択肢**
7. 使わなくしたルートは、日の編集パネルの「出勤（…）」、一括設定の出勤のルート、追加の移動の「ルートから選ぶ」のどれにも出ない。
8. 使うルートが1件も無いとき、一括設定は今までの「ルートが無いので、出勤は選べません。」を出す。
9. 戻したルートは、7 の3か所にまた出る。

**過去の記録（変わらないこと）**
10. 使わなくしたルートで出勤にしていた日は、月次画面（カレンダー・表）で今までと同じルート名・金額で表示される。月の合計と CSV も、使わなくする前と同じ。
11. その日の編集パネルでは、現在の選択として記録のコピーの名前が選択済みで出る。

**API**
12. `GET /api/routes` は既定で使うルートだけを返し、`?includeArchived=true` で使わなくなったものも `archived: true` で返す。ほかの値は 400。
13. `PATCH /api/routes/:id` に `{ "archived": true }` で使わなくなり、`false` で戻る。同じ状態への再実行も 200。存在しない id は 404。`archived` が真偽値でないときは 400。
14. 使わなくなったルートへの `PUT /api/routes/:id` は 409、`DELETE` は 204。
15. 使わなくなったルートを出勤に指定する `PUT /api/daily-records/:date`・`POST /api/daily-records/bulk`・`POST /api/daily-records/bulk/preview` は 400（`workStyle.routeId` / `days[i].workStyle.routeId`）。存在しないルートは今までどおり「選んだルートが見つかりません」。
16. 既存の DB（マイグレーション3まで適用済み）で backend を起動すると、データを残したまま version 4 が適用され、すべてのルートが `archived: false` になる。

**テスト・規則**
17. 次のテストを書く（Vitest）。
    - `SqliteRouteRepository`: `setArchived` の両方向、`list` の既定と `includeArchived`、存在しない id
    - マイグレーション: version 3 の DB に4を適用しても行が残る
    - `route-router`: PATCH の正常・400・404、PUT の 409、GET のクエリ
    - `resolveWorkStyle` と各 daily-records のルーター: 使わないルートの 400
    - フロント: ルートを「使う／使わない」に分ける純粋関数（`routes/` に置く）と `routes-api` の呼び出し
    - `openapi.test.ts` が通る（`openapi.yaml` を直す）
18. `npm run typecheck && npm run lint && npm run test` が通る。
19. `docs/troubleshooting.md`・`docs/api/openapi.yaml` が実装と合っている。
