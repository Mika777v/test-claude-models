# SPEC: 使わなくなったルートを片付ける

状態: オーナー確認前の案（下の「おすすめ」を採用した前提で書いてある）

## 0. 調べて分かったこと

- **「削除」は既にある。** F1 でルートの登録・一覧・編集・削除ができ（`DELETE /api/routes/:id`、`RoutesPage.tsx` の削除ボタン＋確認ダイアログ）、過去の記録はスナップショットを持つので削除しても変わらない（U7）。
- それでも「ごちゃごちゃ」が起きている。考えられる理由:
  1. 削除に気づいていない／1件ずつ確認が出るのが面倒。
  2. 消したくない（取り消せない・過去の客先ルートを後で使うかもしれない・`searchUrl` を残したい）ので消せずにいる。
- ごちゃごちゃしている場所は2つ: ①ルート管理画面の一覧 ②出勤の選択肢（`DayPanel` の勤務区分、`BulkDialog` のルート選択、追加の移動の「ルートから選ぶ」。どれも `listRoutes()` の結果を使う）。
- 「勤務区分は削除済みルートのコピーをそのまま表示する」(U7) ので、選択肢から外れても過去の記録の表示は壊れない。`DayPanel.buildOptions` は、記録が持つルートが一覧に無いときも選択肢に残す作りになっている。

## 2. 要件（おすすめを採用）

### やること

1. ルートに「使わない（アーカイブ）」状態を足す。
   - 型: `Route` に `archived: boolean`（`shared/src/route.ts`）。`RouteInput` には含めない（編集では変えない）。
   - DB: マイグレーション **version 4** で `ALTER TABLE routes ADD COLUMN archived_at TEXT`（NULL = 使っている）。既存の行は NULL のまま（今までのルートは全部「使っている」）。`routes` への外部キーは無いので他テーブルは変えない。
2. API（`docs/api/openapi.yaml` も同じ PR で更新。OpenAPI と「メソッド＋パス」の一致のテストがあるため）
   - `GET /api/routes` は **使っているルートだけ** を返す（現状の呼び出し元＝カレンダー・一括設定・追加の移動が自然にすっきりする）。`?includeArchived=true` で全部。
   - `POST /api/routes/:id/archive`（204、無ければ 404「ルートが見つかりません」）。
   - `POST /api/routes/:id/restore`（同上）。
   - すでにその状態でも成功（冪等）。
   - 既存 `DELETE /api/routes/:id` は残す（アーカイブ済みでも消せる）。
   - `PUT /api/routes/:id` はアーカイブ済みなら 409「使わないルートは編集できません。先に戻してください」。
   - 日次記録の作成・更新、一括登録で `workStyle.routeId` がアーカイブ済みなら 400（`routeId` のフィールドエラー「このルートは使わない設定になっています」）。`resolve-work-style.ts` で `routes.get` の結果を見て判定。追加の移動はコピー入力なので `sourceRouteId` は検証しない。
3. 画面
   - ルート管理画面: 各ルートに「使わない」ボタン（確認ダイアログ無し。取り消せるので、実行後に「元に戻す」を通知に出す）。一覧の下に折りたたみ「使わないルート（N件）」。中には「戻す」「削除」（削除は既存の確認付き）。
   - 出勤の選択肢（`DayPanel`・`BulkDialog`・`ExtraTripForm`）にはアーカイブ済みを出さない。ただし日の編集パネルでは、その日の記録が使っているルートは今まで通り選択肢に残す（`buildOptions` のまま）。
4. 文書（同じ PR）
   - `docs/requirements.md`: F1 に「使わないルートを隠す・戻す」、5. データの項目の Route に `archived`、決定の記録に **U11**、更新日。
   - `docs/adr/0004-archive-routes.md`（下記「戻しにくい変更」）と `docs/adr/README.md` の表。
   - `docs/troubleshooting.md`: 追加する 409 と 400 のメッセージを表に足す。
   - `docs/PROGRESS.md` を更新。

### やらないこと

- 複数選択での一括アーカイブ／一括削除（Q1 の C）。必要になったら別 Task。
- 記録側の変更、記録に使われている件数の表示、ルートの並べ替え、期間指定の自動アーカイブ。
- 認証・複数ユーザー（`userId` は今のまま固定値）。
- `searchUrl` や `RouteSnapshot` の変更（スナップショットに `archived` は入れない）。

### 受け入れ条件

- [ ] 「使わない」を押すと、ルート管理の一覧から消え、「使わないルート」の折りたたみに移る。再読み込みしても保たれる。
- [ ] 「戻す」で一覧に戻り、出勤の選択肢にも再び出る。
- [ ] アーカイブ済みルートは、日の編集パネルの勤務区分・一括設定のルート選択・追加の移動の「ルートから選ぶ」に出ない。
- [ ] アーカイブ済みルートで過去に作った記録は、金額・区間・ルート名がそのまま表示され、その日の編集パネルでは選択肢に残る。月の合計・CSV は変わらない。
- [ ] アーカイブ済みルートの `routeId` で記録を作る／一括登録すると 400。編集（PUT）は 409。存在しない id は 404。
- [ ] 既存データで migration 4 が通り（PRAGMA user_version = 4）、既存ルートは全部「使っている」。migrations のテストを足す。
- [ ] テスト: リポジトリ（archive/restore/list のフィルタ・冪等）、ルーター（各ステータス）、`resolve-work-style`（拒否）、フロントのフォーム・API クライアントの純粋関数、`openapi.test.ts` が通る。
- [ ] `npm run typecheck && npm run lint && npm run test` が通る。

## 3. 戻しにくい変更（要オーナー確認）

次は **自動マージせず、オーナーが読んでからマージする** PR にする（`CLAUDE.md`）。

1. **DB のスキーマ変更**: `routes.archived_at` 列の追加（migration 4）。追加のみで既存データは壊れないが、一度 main に入れた番号の SQL は書き換えない決まりなので、後からの修正は migration 5 になる。
2. **要件定義の変更**: `docs/requirements.md` の F1・Route・決定の記録（U11）。
3. **ADR-0004（新規）**: 「ルートを物理削除でなく『使わない』フラグで片付ける。理由・採った案（`archived_at` 列）、見送った案（削除のみ／別テーブルへ移動／`archived` 真偽値）」。`archived_at` を日時にした理由は、いつ隠したか分かり、`created_at`/`updated_at` と揃うため。
4. 作業の分け方（1 作業 = 1 PR）の案: ① ADR・要件・migration・型・リポジトリ・API（上記 1 を含むのでオーナー確認）→ ② 画面。①を先にマージしてから②。
